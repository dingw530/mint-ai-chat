# 摄入任务重试、状态细化与 Chat 斜杠命令

## 背景与目标

当前摄入任务虽然已经持久化了任务阶段，并已有失败任务重试 API，但用户界面没有在失败任务上提供可见的重试动作；Chat 中的摄入任务运行态主要依赖一个小动画点，难以判断任务是否仍在执行；`AI 编译中` 也无法说明任务正在做什么。与此同时，用户需要在对话框中快速调用 Wiki 相关工具。

本变更的目标是让用户能够：

1. 对单条失败摄入任务执行可靠重试，并在三个已有入口看到结果。
2. 看到容易理解的当前摄入阶段，而不是笼统的“AI 编译中”。
3. 在 Chat 输入框输入 `/`，选择并编辑 Wiki 工具命令后发送。
4. 在不强制展开固定区域的前提下，明显感知 Chat 摄入任务正在运行。

## 用户与场景

- 用户从 Wiki 或 Chat 发起摄入，任务进入排队、解析、编译和提交阶段。
- 任务失败后，用户在任务中心、任务详情或 Chat 摄入卡片中点击“重试”。
- 用户在 Chat 输入框输入 `/wiki_search React`、`/wiki_ingest ...` 等自由文本命令，确认后由 Agent 按既有工具权限与审批流程处理。
- 用户切换或收起 Chat 中的摄入任务固定区域，仍能从区域头部和任务卡片识别运行状态。

## 用户故事

- US-001：作为摄入任务用户，我希望针对某一条失败任务重试，以便恢复处理而不用重新提交来源。
- US-002：作为摄入任务用户，我希望看到“正在整理资料、正在核对原文、正在生成知识页面”等明确状态，以便知道任务卡在哪里。
- US-003：作为 Chat 用户，我希望输入 `/` 选择 Wiki 工具并编辑自由文本参数，以便快速表达工具意图。
- US-004：作为 Chat 用户，我希望运行中的摄入任务有清晰文字、百分比和进度反馈，即使我不展开任务区域也能识别它正在运行。

## 功能范围

### FP-001：单条失败任务重试

- 失败状态和部分失败状态的任务在任务中心任务行、任务详情抽屉、Chat 摄入任务卡片都显示“重试”。
- 点击重试只作用于当前任务，保留原任务 ID、原始来源和原始输入参数，重置为排队状态并立即显示“等待重试”。
- 重试按钮在请求期间禁用，失败时显示可理解的错误；其他任务不发生状态变化。
- 原始暂存输入必须可用于重试；任务成功后或用户移除任务时清理暂存输入，不把暂存输入当作正式 Wiki 来源。

### FP-002：摄入状态文案

活动任务的当前步骤使用以下用户文案：

| 内部阶段 | 用户文案 |
|---|---|
| 排队/恢复 | 等待处理 |
| 解析与准备 | 正在整理资料 |
| 编译第一阶段 | 正在整理资料 |
| 证据与内容校验 | 正在核对原文 |
| 页面分类、关系、合并与写入前整理 | 正在生成知识页面 |
| 提交 | 提交 Wiki 中 |
| 成功 | 已完成 |
| 部分失败 | 部分完成，请检查 |
| 失败 | 处理失败 |

三段编译状态必须来自实际编译执行顺序，不能只在前端定时轮换文案。

### FP-003：Chat 摄入任务运行态

- Chat 固定区域仍可手动收起，不因任务运行而强制保持展开。
- 展开时，活动任务卡显示“正在处理”、当前步骤、百分比、明显进度条和当前任务名称。
- 收起时，区域头部仍显示活动任务数量与“处理中”文字，不只显示动画点。
- 活动态使用可访问的 `role="status"` 或等价语义，动画不能是唯一状态信号。

### FP-004：斜杠命令

- 输入框输入 `/` 时展示命令面板，首批只包含：`/wiki_ingest`、`/wiki_search`、`/wiki_read`、`/knowledge_graph`。
- 选择命令后，将命令前缀插入输入框，用户继续编辑自由文本参数后再发送。
- 命令定义通过通用注册结构驱动名称、说明、工具映射、参数提示和发送解析，不在输入框组件中写死分支。
- 发送时保留用户可见的原始命令文本；服务端只接受白名单命令元数据，并通过既有 Agent/ReAct、工具策略和审批流程执行，不绕过权限。
- 不在本变更中加入 Bash、文件读写或 MCP 命令。

## 非目标

- 不实现工具的直接执行面板，不跳过 Agent 或工具审批。
- 不新增工具、不改变工具参数 schema、不改变工具权限和审批策略。
- 不实现完整摄入时间线、详细日志流或单个失败子项独立重试。
- 不新增数据库表或迁移；复用现有 ingestion job、payload、HTTP 和 Electron IPC 入口。
- 不强制 Chat 摄入区域展开，不改造普通 Agent 运行状态条。

## 业务规则

- BR-001：重试只能作用于 `failed`、`error` 或 `partial_failed` 的指定任务；活动任务、成功任务和取消任务不可重试。
- BR-002：重试复用当前任务 ID 和持久化 payload，不创建第二条任务记录；点击一次只入队一次。
- BR-003：失败任务的原始暂存输入在重试窗口内保留在 `ingestion-pending/`，成功后转为正式来源或清理；删除任务时只清理其暂存输入，不删除正式来源和 Wiki 页面。
- BR-004：`step` 文案必须由后端任务/编译器进度事件更新，客户端展示后端当前值，不自行猜测阶段。
- BR-005：斜杠命令名称必须匹配注册白名单；未知命令按普通文本处理或给出可理解的命令提示，不能让客户端传入任意工具名。
- BR-006：斜杠命令只表达工具意图；实际执行仍受当前 Agent 的工具集合、工具策略、审批和错误处理约束。
- BR-007：Chat 和 Wiki 两个 UI 入口共享任务详情与重试 API；HTTP 和 Electron IPC 的结果形状保持一致。

## 验收标准

- AC-001：失败任务在任务中心显示“重试”；点击后对当前任务发起一次重试请求，任务变为“等待重试/排队中”，其他任务保持原状态。
- AC-002：同一失败任务在详情抽屉和 Chat 摄入卡片也显示“重试”；请求中按钮禁用，成功或失败结果可见，重复点击不会创建重复入队。
- AC-003：后端重试复用原任务 ID、payload 和原始来源；上传/Chat 文件在失败后仍可被重试读取，成功后不遗留该任务的暂存输入。
- AC-004：活动任务按真实执行顺序展示“正在整理资料 → 正在核对原文 → 正在生成知识页面”，随后进入“提交 Wiki 中”和终态；客户端不定时伪造状态。
- AC-005：Chat 摄入卡片展开时显示当前状态文案、百分比、明显进度条和任务名称；收起时仍显示活动任务数量及“处理中”文字，动画不是唯一信号。
- AC-006：用户在 Chat 输入 `/` 可看到四个白名单命令；选择后命令文本可编辑；发送 `/wiki_search React` 等自由文本后，既有 Agent 工具调用链收到对应命令意图，且不绕过审批。
- AC-007：未知命令、空参数、失败任务重复重试和不存在任务等边界有明确处理与测试覆盖。
- AC-008：客户端、服务端、Electron HTTP/IPC 兼容路径、A2UI 摄入状态和既有任务中心/Agent 回归测试通过；本变更 Harness 的 unit、browser-ac、coverage、boundary 通过。

## 风险与依赖

- 现有重试方法和前端 API 已存在，但失败流程会清理暂存文件；若不调整生命周期，UI 重试会成为不可执行的假动作。
- 编译器目前通过一次 `compileSource` 调用完成多个子阶段，需要增加受控进度回调，避免客户端凭时间切换文案。
- 斜杠命令需要扩展现有消息发送元数据，并同时兼容 HTTP SSE 与 Electron IPC；不应新增另一套聊天发送协议。
- A2UI 任务模型、共享任务中心和详情抽屉都消费 `step/status`，字段兼容和旧任务脏数据必须保留安全 fallback。

## 非功能要求

- NF-001：HTTP 和 Electron IPC 对重试任务、斜杠命令元数据和既有消息/审批控制保持一致的结果形状。
- NF-002：任务暂存输入只能在当前 Wiki 根目录的受控路径内保留；成功或移除后清理，不影响正式 sources/pages。
- NF-003：斜杠命令不得绕过 Agent 工具集合、工具策略、审批、取消和错误处理。
- NF-004：活动状态必须由文字和数值/进度条表达，动画只能作为辅助反馈。
