# WikiLintTool 重构复盘经验

> 日期：2026-06-26
> 涉及模块：WikiSearchTool、WikiLintTool、BashTool、messageService
> 核心主题：AI 工具设计的可靠性与架构演进

---

## 一、问题链全景

### 起点：wiki_search 调用频率过高

用户发现 LLM 查看多篇 Wiki 文章时逐篇调用 `wiki_search`，默认 `maxIterations=5` 很快耗完。初始方案（方向一+二）是改工具描述引导 LLM 批量/并行调用，效果不明显。

### 暴露的深层问题

逐层排查后发现一系列相互关联的问题：

1. **文件名不参与搜索评分** — 按文章名搜索时命中率低，LLM 需多次换关键词
2. **LLM 主动设 `maxResults=1`** — 每轮只看到一个结果，错了就再来一轮
3. **paths 模式有 validation bug** — `question` 为必填字段，导致无 question 时调用失败
4. **内容截断** — 4000 字符内部截断 + 8000 字符响应截断，LLM 认为内容不全
5. **BashTool 拦截有漏洞** — 只检查绝对路径，`cd` 进目录后用相对路径可绕过
6. **WikiLintTool 路径解析错误** — `../../` 未 resolve，大量误报断裂链接
7. **WikiLintTool pageNames 顺序问题** — 边遍历边检查，目标文件未注册时误报

### 终点：架构级重写

lint 工具最终放弃了自行判断文件存在性，改为委托 `WikiSearchTool` 批量验证。

## 二、技术教训

### 教训 1：共享事实源，不复刻实现

lint 尝试独立判断文件是否存在——与 wiki_search 访问同一文件系统、解析同一路径。两套代码互相独立时细节差异是必然的。

**判断标准**：如果两段代码做的是同一件事（检查文件是否存在），它们应该共享同一个实现，而不是各写各的。

**案例**：lint 的断裂链接检测经历了三次修复（`../` 解析、遍历顺序分离、`.md` 输出统一），仍然不可靠。最终改为 `WikiSearchTool.execute({ paths })` 一次性委托，不再自行判断。

**原则**：任何需要判断文件/资源存在的逻辑，统一委托给系统里唯一做这件事的模块。

### 教训 2：截断是一种"软故障"

4000 字符截断 + 8000 字符响应截断两层叠加。不是报错，而是返回不完整的数据。LLM 的应对不是"报错重试"，而是"换工具绕过"（转用 bash 自行读取）。

**识别特征**：
- 数据看起来对了，实际不完整
- LLM 行为突然改变（如从 wiki_search 切换到 bash）
- 没有错误日志，因为系统层面没有报错

**应对方案**：
- 所有涉及 LLM 上下文的截断点显式可配置
- 截断时返回明确的截断标记和剩余长度信息
- 关键截断点（内容限、响应限）应该在文档中统一列出

### 教训 3：渐进式 bug 需要系统性测试策略

三个 bug（`../` 未解析、遍历顺序依赖、`.md` 输出不一致）在 3-5 个文件的 wiki 上都无法复现。这不是函数写错了，而是组合条件和规模触发的。

**典型特征**：
- 小型测试通过，中型测试偶发失败
- 错误报告看起来"不一致"而非"全错"
- 用户描述是"经常不准"而非"功能坏了"

**应对方案**：
- 文件扫描/路径解析逻辑的测试 fixture 覆盖边界规模（10+ 文件、嵌套目录、交叉链接）
- 引入随机顺序遍历测试，暴露顺序依赖
- 对路径字符串处理做显式的 Unicode 和跨平台测试

### 教训 4：补丁有隐含的重构阈值

三次修复后问题仍在。不是修复不对，而是修复框架本身有缺陷——lint 在维护自己的 `pageNames` 集合用于文件存在性判断，但这个集合没有任何权威性。

**判断阈值（满足任意一条应重新审视架构）**：
1. 同一个模块连续修了 3 次还在报同类错误
2. 修复涉及的能力系统里其他模块已实现好
3. 每次修复的代码量在增长但问题域没有收窄

**应对方案**：停下手头的修复，问自己"这个模块做的事，系统里有谁已经做过了？"

## 三、功能设计教训

### 教训 5：工具职责的"狭窄化"原则

lint 最初追求全面覆盖，但每个检查项的可靠性不同：

| 检查项 | 可靠性 | 原因 |
|--------|--------|------|
| 缺少 frontmatter | 高 | 读文件开头几个字节，无状态依赖 |
| Schema 标签合规性 | 高 | 解析 frontmatter 字符串，无外部依赖 |
| 未编译 source | 高 | 文件列表比对，纯集合操作 |
| 断裂链接 | 低 | 涉及路径解析、跨文件匹配、文件系统状态 |
| 孤立页面 | 低 | 依赖断裂链接的结果 |

**原则**：一个工具只做"可靠的事"。不可靠的检查项要么改为委托（给 wiki_search），要么交给 LLM 自行判断。不要在 lint 工具里堆砌不可靠的检查来追求"全面"。

### 教训 6：工具粒度应匹配 AI 协作模式

一个大工具返回全部结果 vs 多个小工具各做一事——后者更优，因为：
- 每个小调用的结果是权威的
- LLM 可以根据前一步结果动态决定下一步
- 出错时影响范围小，LLM 更容易纠正

**原则**：让每个工具做小、做准。LLM 编排多个工具完成复杂任务。这和微服务的设计哲学一致——只是服务变成了 AI 工具。

### 教训 7：工具输出格式一致性是功能需求

`.md` 后缀在 `file` 字段（有）和 `description` 字段（无）之间不一致，导致 LLM 花费多轮猜测正确格式。

**原则**：
- AI 工具的输出也是 AI 的输入上下文，格式自洽是功能需求
- 每条信息只以一种格式呈现
- 不依赖 LLM 去推断格式间的隐含关系
- 冗余优于歧义

### 教训 8：约束 LLM 行为靠机制不靠劝导

"不要用 bash 读 Wiki 文件"的提示词写在 system prompt 中，LLM 仍然尝试了。不是没读到，而是 LLM 的行为由"效果"驱动——如果它认为另一条路径能拿到更多内容，就会绕过指令。

**原则**：
- 提示词是辅助理解，权限检查是强制约束
- 两者需要并存：提示词说明"已被拦截，会报错"，权限检查实际拦截
- 光靠提示词枚举"禁止操作"是不够的，需要在系统层面让这些操作不可行

### 教训 9：从第一天预留可扩展架构

lint 这类工具的设计模式应该是"可扩展检查器"而非"全量扫描器"：
- 检查项可插拔、可独立启用/禁用
- 先上简单可靠的检查
- 复杂检查逐步加入或委托出去

**案例**：如果 lint 第一天就设计为检查器注册模式，断裂链接作为一个独立检查器注入，后续发现不可靠时只需移除该注册项，不影响其他检查。而不是在同一个 `execute` 方法里层层打补丁。

## 四、总结

```
技术层面：共享实现 > 复刻逻辑  |  显式截断 > 静默截断  |  规模测试 > 单点测试
设计层面：狭窄可靠 > 全面模糊  |  小粒度 > 大粒度    |  权限拦截 > 指令劝导
架构层面：预留可扩展          |  及时识别重构阈值    |  格式自洽是功能需求
```

## 五、问题根源追溯：2026-06-18 设计文档

### 问题 1：lint 断裂链接检测逻辑不完整

**设计文档原文**（design-doc.md）：
> wiki_lint 检查项：孤立页面、断裂链接（链接目标文件不存在）

**exec-plan 原文**：
> wiki_lint：扫描所有 .md 文件，检查孤立页面和断裂链接

**根源**：设计文档只说了"检查断裂链接"，但没定义检测方法。实现时选择了"解析 Markdown 链接 → 匹配 pageNames"的方案，但这个方案在路径解析规范、遍历顺序、`.md` 处理策略上都没有设计约束。每个细节都是实现者自由发挥，导致了三个渐进式 bug。

**教训**：当设计文档说"检查 X"但没有定义"怎么检查"时，实现方案的质量完全取决于实现者的运气。对关键检查项，设计阶段就应该明确检测策略。

### 问题 2：wiki_query 缺少文件名权重设计

**设计文档原文**（design-doc.md）：
> wiki_query 流程：关键词提取 → grep 搜索 → 读取匹配文件

**exec-plan 原文**：
> wiki_query：用 Node.js fs 进行文件名 + 内容关键词匹配

**根源**：exec-plan 写了"文件名 + 内容关键词匹配"，但设计文档只写了"grep 搜索"。实现时以设计文档为准，只做了内容关键词匹配，文件名评分被遗漏。exec-plan 的"文件名 + 内容"约束没有落实到实现。

**教训**：exec-plan 和 design-doc 对同一功能的描述不一致时，实现者倾向于遵循 design-doc（更详细）。exec-plan 中的细节约束应该同步到 design-doc。

### 问题 3：无共享基础设施层

**设计文档原文**（design-doc.md）：
> 文件工具和 Wiki 工具注册到 ToolRegistry，归入内置工具

**根源**：设计只关心了"工具注册到 ToolRegistry"，没有考虑"文件存在性检查"这个公共能力应该提取为共享服务。结果 read_file、wiki_query、wiki_lint 各自实现了自己的文件访问逻辑。

**教训**：多个工具需要访问同一资源（文件系统）时，设计阶段应识别共享能力层。不是所有工具各自实现一套，而是提取公共基础设施。

### 问题 4：截断限制无文档化

**根源**：4000 字符的内容截断和 8000 字符的响应截断在设计文档中均无提及。这些限制是在实现和后续迭代中引入的，但没有在任何设计文档中记录。导致后面排查时花了大量时间才定位到截断是 LLM 转用 bash 的触发原因。

**教训**：所有影响 LLM 行为的限制值（截断、超时、重试次数）都应显式文档化。不文档化的限制就是隐藏的故障点。

### 问题 5：缺少 LLM 引导策略设计

**根源**：设计文档没有讨论"如何引导 LLM 正确使用 Wiki 工具"。system prompt 中的 Wiki guide 是后来逐步叠加的，而不是设计阶段规划的。同样，BashTool 的拦截逻辑也是后来补的。

**教训**：AI 工具的引导策略（提示词 + 权限约束）应该是设计阶段的一部分，不是实现阶段的补充。

## 六个设计缺陷的链式影响

```
设计阶段缺失                         实现阶段的后果
─────────────────────────────────────────────────
① lint 断链检测策略未定义     →  路径解析不完整（../ 未 resolve）
② 文件名评分未明确           →  按文章名搜索命中率低
③ 无共享文件访问层           →  各工具自实现，不一致风险
④ 截断限制未文档化           →  内容截断导致 LLM 转用 bash
⑤ LLM 引导策略未规划         →  提示词靠补丁，拦截靠后加
⑥ design-doc/exec-plan 不一致 →  文件名评分被遗漏实现
```

这六个问题在设计文档中埋下，在实现中逐个暴露，在后续迭代中逐个修补。每个单看都不致命，但组合起来导致了 lint 工具的全面不可靠和多次返工。

## 六、对 SDD 过程的设计要点

从本次 WikiLintTool 的复盘可以提炼出以下 SDD 过程中需要特别注意的设计要点：

### 要点 1：设计文档必须定义"怎么做"，不止"做什么"

设计文档中说"检查断裂链接"、"检查孤立页面"，但没说具体的检测策略。实现者有多种选择，每种有不同的可靠性和边界条件。

**SDD 检查点**：每个功能点至少包含检测策略描述。如果是"检查X"，需写清检测方法、判断标准、误报/漏报的边界条件。不可将检测策略完全交给实现阶段决定。

### 要点 2：exec-plan 与 design-doc 必须对同一功能的描述一致

exec-plan 写了"文件名+内容关键词匹配"，但 design-doc 只写了"grep 搜索"。实现者以 design-doc 为准，文件名评分被遗漏。

**SDD 检查点**：设计定稿后，exec-plan 起草时应与 design-doc 逐项比对，确保描述不矛盾。exec-plan 中的新增细节应反哺到 design-doc 中更新。

### 要点 3：设计阶段识别共享能力，避免工具间各自实现

三个工具各自做了文件存在性检查。没有公共的文件访问层，导致 lint 的路径判断与 wiki_search 不一致。

**SDD 检查点**：设计阶段对候选工具列表做能力分析，标出哪些工具需要同样的基础能力。这类能力应设计为共享模块，而非在各工具中各自实现。

### 要点 4：影响 LLM 行为的关键参数必须显式文档化

4000 字符内容截断、8000 字符响应截断在设计文档和 exec-plan 中都没有提及。这些参数直接决定了 LLM 能否拿到完整内容。

**SDD 检查点**：设计文档应列出所有影响 LLM 行为的参数清单（截断值、超时、重试次数、返回条数上限）。不文档化的限制就是隐藏的故障点。

### 要点 5：AI 工具的引导策略是设计的一部分，不是实现的补充

system prompt 中的 Wiki guide、BashTool 的拦截逻辑都是后来补的，而非设计阶段规划的。

**SDD 检查点**：设计阶段应包含"引导策略"一节：LLM 需要理解哪些规则（prompt 层面）、哪些需要系统层面强制执行（权限拦截）、哪些信息需要显式提供给 LLM。

### 要点 6：工具的返回格式设计应视为 LLM 上下文设计

.md 后缀的不一致误导了 LLM，使其花费多轮猜测正确格式。AI 工具的输出同时是 LLM 的输入上下文。

**SDD 检查点**：设计文档中为每个工具的返回格式标注"LLM 上下文一致性检查"——同一份输出中不要出现矛盾的格式暗示。

### 要点 7：设计阶段规划工具的可靠性等级

lint 的五个检查项可靠性各不相同，但设计文档中没有区分。

**SDD 检查点**：每个工具的功能模块应标注可靠性等级：高（纯文件操作）、中（跨文件匹配）、低（涉及解析推测）。低可靠模块应设计为可独立移除或委托。

### 要点 8：多轮补丁后应设架构重评估节点

lint 在三次补丁修复后仍然不可靠，但没有一个机制触发架构反思。

**SDD 检查点**：在 exec-plan 中为每个模块标注补丁计数器阈值。当某模块的返工次数达到阈值（如 3 次）时，应自动触发架构重评估。

## SDD 流程检查清单（基于本次复盘）

```
设计阶段
  每个功能点写清检测策略（不仅"做什么"，还有"怎么做"）
  对候选工具做能力分析，识别共享模块
  列出影响 LLM 行为的关键参数及其限制值
  包含 LLM 引导策略（prompt 层 + 系统层）
  标注每个功能模块的可靠性等级
  工具的返回格式做 LLM 上下文一致性检查
  为复杂模块标注补丁计数器阈值

执行阶段
  exec-plan 与 design-doc 逐项比对一致性
  exec-plan 新增细节反哺到 design-doc
  共享模块先于独立工具实现

验收阶段
  检查设计文档中声明的关键参数是否落实
  检查引导策略是否已实施（prompt + 拦截）
```
