# Product Spec: SQLite 迁移失败关闭

## 背景与目标

当前 `runMigrations()` 只对无法归类为幂等兼容的迁移错误打印日志，然后继续执行后续迁移与数据库初始化。这可能让 `_migrations` 记录、实际 schema 和后续 seed/业务读写处于不一致状态。

本变更落实 TD-002：保留新库/既有库所需的幂等兼容路径，但任何非幂等迁移失败都必须中止本轮初始化并向调用方暴露明确错误；兼容跳过与真实失败均有可区分日志和自动化证据。

## 用户与场景

- 启动已有 Mint 数据库的本机用户。
- 新建数据库或升级跨多个历史版本数据库的维护者。
- 通过 Node、Electron、CLI、测试或后台服务首次触发 `getDb()` 的调用方。

## 用户故事

- US-001：作为 Mint 用户，我希望数据库升级失败时应用拒绝继续使用不一致的 schema，而不是带着隐患运行。
- US-002：作为维护者，我希望“对象已存在”的兼容迁移与真实迁移故障在日志和测试中明确区分。
- US-003：作为故障排查者，我希望错误包含迁移 ID、名称和原始原因，但不泄露数据库内容。

## 功能范围

### FP-001：非幂等迁移 fail-closed

1. 未应用迁移抛出非兼容错误时，`runMigrations()` 必须立即抛错并停止循环。
2. 失败迁移不得写入 `_migrations`，其后的迁移不得执行。
3. `getDb()` 不得在迁移失败后执行 seed 或向同进程调用方返回可用数据库句柄。

### FP-002：幂等兼容与日志

1. 既有 `duplicate column` / `already exists` 兼容语义继续支持全新 schema 与旧库升级。
2. 兼容跳过必须写入该迁移记录，并输出包含迁移 ID、名称及“兼容跳过”语义的独立日志。
3. 非幂等失败日志与兼容日志必须使用不同级别/前缀，便于测试和排障区分。

### FP-003：初始化故障可恢复性

1. 初始化失败后不得缓存一个被当作成功的单例。
2. 同进程后续重试必须重新进入初始化流程，或持续得到明确的初始化失败；不得静默返回失败现场的连接。

## 非目标

- 不增加、删除或重排 migration ID，不修改业务 schema。
- 不解决 `createSchema()` 与 migrations 的双源真相（TD-021）。
- 不引入通用迁移框架、自动 schema 修复、备份/回滚产品流程或新的数据库 API。
- 不把 sqlite-vec 扩展不可用改为致命错误；其现有关键词降级语义保持不变。

## 业务规则

| ID     | 规则                                                                               |
| ------ | ---------------------------------------------------------------------------------- |
| BR-001 | 只有明确识别为既有对象/列的兼容错误可转为已应用；其他错误一律重新抛出。            |
| BR-002 | 非幂等错误发生后，失败迁移与后续迁移不得新增 `_migrations` 记录。                  |
| BR-003 | 对外错误必须包含迁移 ID、迁移名称和原始错误摘要，不能包含 SQL 数据值或数据库内容。 |
| BR-004 | 兼容跳过必须被记录为可观察事件，不能无日志吞掉。                                   |
| BR-005 | 数据库初始化只有在 schema、迁移和 seed 全部成功后才可被视为可用。                  |

## 非功能要求

| ID     | 要求                                                 |
| ------ | ---------------------------------------------------- |
| NF-001 | 既有成功迁移与新库初始化行为保持兼容。               |
| NF-002 | 错误分类逻辑应为小型、确定、可单元测试的纯判断。     |
| NF-003 | 迁移失败不得被后续调用掩盖；失败路径必须可重复验证。 |

## 验收标准

- AC-001：给一个未应用迁移制造非 `duplicate column` / `already exists` 错误时，`runMigrations()` 抛出包含迁移 ID、名称和原始原因的错误，且不执行后续迁移。
- AC-002：AC-001 的失败迁移与后续迁移均没有新增 `_migrations` 记录；调用方不能获得被标记为成功初始化的数据库。
- AC-003：制造 `duplicate column` 或 `already exists` 兼容场景时，该迁移被记录为已应用，后续迁移继续执行，并产生独立的兼容跳过日志。
- AC-004：迁移真实失败时产生与兼容日志可区分的失败日志；日志不包含表中数据值或密钥。
- AC-005：迁移定向测试、数据库相关回归、server typecheck 与完整 Harness 的 unit、coverage、boundary 均通过；本变更无 UI 行为，browser-ac 以空场景记录为不适用。

## 风险与依赖

- GitNexus 对 `runMigrations` 的上游分析为 **CRITICAL**：258 个受影响符号、1 个直接调用方 `getDb`、66 条流程、8 个模块。用户已确认在该风险范围内继续，执行必须保持窄改动并跑数据库与完整 Harness 回归。
- 当前迁移兼容分支承担“`createSchema()` 已创建现行列/对象后再补 `_migrations` 记录”的职责，不能简单删除。
- SQLite 部分 DDL 已可能在失败前生效；本变更保证停止和不谎报成功，不承诺为所有历史迁移增加自动事务回滚。
