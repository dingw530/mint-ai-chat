# 产品规格：知识摄入异步任务管理与 Chat 任务卡片

| 属性 | 值 |

| 状态 | 已实现并通过 verify |

## 背景与目标

- 业务背景：Mint 当前支持文件上传和 Chat 中调用 `wiki_ingest` 两种知识摄入入口。知识解析、AI 编译、图谱构建和 Wiki 写入可能持续较长时间。
- 当前问题：大文件或多个摄入任务会占用同步工具调用；任务状态难以统一管理；应用重启后任务状态可能丢失；多个任务并发写入 Wiki 时存在一致性风险。
- 目标：建立统一的知识摄入任务管理能力。第一阶段在知识库界面提供任务看板；第二阶段基于 A2UI 协议在 Chat 中展示任务卡片。
- 成功标准：上传和 Chat 两种入口创建的任务均可在知识库任务看板中查询、跟踪和处理；Chat 在第一阶段只返回“已加入任务”的简短反馈；第二阶段 Chat 任务卡片可以展示同一任务的状态和结果。

## 用户与场景

- 目标用户：使用 Mint 管理个人 Wiki 知识库的用户。
- 典型场景：用户上传一个大文件、多个文件，或在 Chat 中要求系统整理资料；系统立即接收任务，用户在知识库任务看板查看处理进度和结果。

## 用户故事

- **US-001**：作为知识库用户，我希望通过文件上传创建摄入任务，从而不需要持续等待页面请求完成。
- **US-002**：作为 Chat 用户，我希望通过 `wiki_ingest` 提交资料后立即获得任务回执，从而可以继续使用 Chat。
- **US-003**：作为知识库用户，我希望在任务看板查看所有入口创建的摄入任务，从而统一了解任务状态、进度和结果。
- **US-004**：作为知识库用户，我希望对失败或排队中的任务进行重试、取消或查看详情，从而处理异常任务。
- **US-005**：作为 Chat 用户，我希望后续在对话中看到摄入任务卡片，从而无需离开 Chat 即可了解任务摘要。

## 范围

### 本次要做

- **FP-001**：统一文件上传和 Chat `wiki_ingest` 的摄入任务创建、状态和结果模型。
- **FP-002**：抽象任务存储和队列适配能力；第一阶段使用本地 SQLite/Node 实现，接口为未来迁移 Redis/BullMQ 保留边界。
- **FP-003**：抽象工具执行模式属性，至少支持 `sync` 和 `async`；`wiki_ingest` 声明为 `async` 工具。
- **FP-004**：第一阶段在知识库模块实现摄入任务看板，展示任务列表、阶段、进度、文件、结果和错误。
- **FP-005**：第一阶段 Chat 中的 `wiki_ingest` 创建异步任务并返回简单工具反馈，不展示 A2UI 任务卡片。
- **FP-006**：第二阶段基于 A2UI 协议在 Chat 中增加任务卡片；任务卡片以业务组件形式注册，不拆解为 Text、Button 等基础组件。
- **FP-007**：第二阶段通过 A2UI `createSurface`、`updateComponents`、`updateDataModel` 和 `deleteSurface` 表达任务卡片生命周期；任务状态仍由统一任务系统提供。

### 本次不做

- 不建设覆盖所有后台任务的通用调度平台，范围仅限知识摄入。
- 第一阶段不引入 Redis、BullMQ 或其他外部队列服务。
- 第一阶段不在 Chat 中展示实时进度卡片。
- 第二阶段不让 A2UI 直接管理任务状态、队列或数据库。
- 不把数据库中的完整 Job 记录直接暴露给 Chat；Chat 使用面向展示的任务视图数据。

## 约束

| 约束类型 | 具体限制 | 违反后果 |
|---|---|---|
| 存储 | 第一阶段继续使用 SQLite，任务状态必须持久化，不能只保存在进程内存中 | 应用重启后任务丢失或状态不可恢复 |
| 队列 | 任务队列必须通过抽象接口访问，不能让业务入口直接依赖具体队列实现 | 未来迁移 Redis/BullMQ 成本上升 |
| 工具 | 工具必须声明 `executionMode`，枚举值为 `sync` 或 `async`；未声明的既有工具按 `sync` 兼容 | 工具执行器和 UI 无法统一判断执行语义 |
| 摄入 | `wiki_ingest` 必须声明为 `async`，执行后立即返回任务受理结果 | Chat 继续被长时间摄入占用 |
| Wiki 写入 | 同一 Wiki 的最终页面、索引、manifest 和图谱提交必须具备一致性保护 | 并发任务可能覆盖或产生不一致内容 |
| Chat 第一阶段 | Chat 仅展示“已加入任务”等简短反馈，完整状态在知识库任务看板查看 | 两个界面出现重复且不一致的任务管理能力 |
| A2UI | 第二阶段使用 A2UI 标准消息 envelope；不得用自定义 `messageType` 替代标准消息类型 | 无法复用标准 A2UI Renderer |
| A2UI 组件 | 任务卡片作为 Mint 业务组件注册在 Catalog 中，组件内部封装基础控件 | Chat 协议暴露过多 UI 细节，组件难以演进 |
| 附件 | 大文件不应通过 Chat 工具参数重复传递完整 Base64 内容；应使用附件引用或服务端已归档文件 | 请求体和上下文膨胀，重试成本高 |

## 校验触发时机

- 文件上传时：校验文件类型、文件大小、Wiki 路径和输入完整性；校验失败时不创建任务。
- Chat 调用 `wiki_ingest` 时：校验输入来源、附件引用、Wiki 配置和权限；校验失败时不创建任务。
- 任务创建时：完成任务 ID、幂等键和初始状态写入后，才向调用方返回受理成功。
- 任务执行时：每个阶段更新任务状态和进度；阶段失败时记录可展示错误。
- 任务操作时：重试、取消等操作必须依据任务当前状态判断是否允许。

## 术语与统一口径

- **摄入任务**：一次由文件上传或 Chat `wiki_ingest` 创建、包含资料解析、AI 编译、图谱构建和 Wiki 提交的后台作业。
- **任务受理成功**：任务记录已持久化并进入 `queued` 或等价的可执行状态；不代表知识已经写入 Wiki。
- **任务完成**：任务的全部必要摄入阶段完成，结果已持久化并可在 Wiki 中查看。
- **部分失败**：批量任务中至少一个输入完成、至少一个输入失败，且系统保留成功结果和失败明细。
- **任务进度**：服务端根据阶段和已处理输入计算的 0 至 100 整数百分比，不承诺与耗时线性对应。
- **Chat 简单反馈**：只说明任务已受理、任务 ID 或文件数量，不展示完整阶段日志和实时进度。
- **A2UI 任务卡片**：第二阶段由 `mint` Catalog 注册、A2UI Surface 承载的 `IngestionTaskCard` 业务组件。

## 数据模型与字段映射

### 工具执行模式

| 字段 | 类型 | 值 | 含义 |
|---|---|---|---|
| `BaseTool.executionMode` | `"sync" | "async"` | `sync` | 工具执行完成后才返回业务结果 |
| `BaseTool.executionMode` | `"sync" | "async"` | `async` | 工具创建后台任务并返回受理结果 |
| `WikiIngestTool.executionMode` | `"sync" | "async"` | `async` | `wiki_ingest` 的固定执行模式 |

### 摄入任务状态

| 字段 | 类型 | 枚举值 | 含义 |
|---|---|---|---|
| `job.status` | string | `queued` | 已持久化，等待 worker 执行 |
| `job.status` | string | `parsing` | 正在解析输入资料 |
| `job.status` | string | `compiling` | 正在调用 AI 编译知识页面 |
| `job.status` | string | `committing` | 正在串行提交 Wiki 文件、索引、manifest 或图谱 |
| `job.status` | string | `completed` | 全部必要阶段完成 |
| `job.status` | string | `partial_failed` | 批量任务部分输入成功、部分输入失败 |
| `job.status` | string | `failed` | 任务无法完成且没有可用成功结果 |
| `job.status` | string | `cancelled` | 用户或系统取消任务 |

### 任务字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `job.id` | string | 全局唯一任务 ID |
| `job.sourceType` | `upload | chat` | 任务创建入口 |
| `job.conversationId` | string/null | Chat 入口关联的对话 ID；上传入口可为空 |
| `job.status` | string | 使用上表枚举 |
| `job.progress` | number | 0 至 100 的整数百分比 |
| `job.step` | string | 当前阶段的用户可读描述 |
| `job.fileCount` | number | 本任务输入文件数量 |
| `job.result` | object/null | 页面数量、源文件、警告等结果摘要 |
| `job.error` | object/null | 错误码、用户可读消息和失败输入明细 |
| `job.createdAt` | ISO 8601 string | 创建时间，使用服务端时区/UTC 约定 |
| `job.updatedAt` | ISO 8601 string | 最近状态更新时间 |
| `job.idempotencyKey` | string/null | 防止同一请求重复创建任务 |

### Chat 工具受理结果

```json
{
  "jobId": "job-456",
  "status": "queued",
  "executionMode": "async",
  "fileCount": 3,
  "message": "已加入知识摄入任务"
}
```

### A2UI 任务卡片数据模型

第二阶段的 A2UI Surface Data Model 使用面向展示的 `/job` 对象，不直接暴露数据库记录：

```json
{
  "job": {
    "jobId": "job-456",
    "status": "compiling",
    "statusLabel": "处理中",
    "progress": 60,
    "step": "AI 编译中",
    "fileCount": 3,
    "result": null
  }
}
```

### 空值与异常口径

- `conversationId` 对上传入口为空；不得用空字符串伪装成真实对话 ID。
- `result` 在任务未进入终态前为 `null` 或缺省；前端不得将缺省结果解释为完成。
- `error` 仅在 `failed` 或 `partial_failed` 状态下展示；没有错误时为 `null` 或缺省。
- `progress` 缺失时按 0 展示；超过 100 或小于 0 的服务端数据视为异常并按边界值处理。
- 已存在任务记录但 worker 未运行时，任务保持 `queued`，由恢复机制重新领取；不得直接标记为完成。
- 任务状态查询不到时，知识库界面展示“任务不存在或已过期”，不得伪造任务完成状态。

## 业务规则

### 规则总表

| 规则 ID | 规则名称 | 说明 |
|---|---|---|
| BR-001 | 双入口统一建任务 | 文件上传和 Chat `wiki_ingest` 必须通过同一任务创建与状态管理能力；不得各自维护独立任务模型 |
| BR-002 | 异步工具快速受理 | `executionMode=async` 的工具只需完成任务持久化和入队即可返回，不等待解析、编译和 Wiki 提交完成 |
| BR-003 | 任务看板为事实来源 | 第一阶段知识库任务看板展示服务端任务状态；Chat 的简单反馈不承担完整状态管理 |
| BR-004 | 阶段状态单向推进 | 任务按 `queued → parsing → compiling → committing → completed` 推进；异常可进入 `partial_failed`、`failed` 或 `cancelled` |
| BR-005 | 成功与失败分项保留 | 批量任务中单个文件失败不得删除或回滚其他已成功且已提交的结果；失败输入需在任务详情中单独展示 |
| BR-006 | 最终提交受保护 | 多个任务可以排队等待，但同一 Wiki 的最终写入必须避免互相覆盖 |
| BR-007 | 重试有边界 | 只有 `failed`、`partial_failed` 或明确可重试的任务允许重试；`completed` 任务不得无条件重复执行 |
| BR-008 | 取消有边界 | `queued`、`parsing`、`compiling` 任务可请求取消；已进入不可逆提交阶段的任务取消结果由设计阶段定义，并必须在看板中反馈 |
| BR-009 | A2UI 只做展示 | 第二阶段 A2UI 仅表达 Surface、组件和 Data Model；任务状态、权限和操作仍由任务系统与业务 API 校验 |
| BR-010 | 工具模式向后兼容 | 未声明 `executionMode` 的既有同步工具按 `sync` 处理，不改变现有工具行为 |

## 错误消息 Contract

### 展示格式

任务错误至少包含：`code`、`message`，批量任务可包含 `items[]` 失败明细。

### 标准错误文案

| 场景 | 错误码 | 文案 |
|---|---|---|
| Wiki 路径未配置 | `WIKI_PATH_NOT_CONFIGURED` | `Wiki 路径未配置，无法创建摄入任务` |
| 文件类型不支持 | `WIKI_FILE_TYPE_UNSUPPORTED` | `不支持的文件类型：{extension}` |
| 文件超过大小限制 | `WIKI_FILE_TOO_LARGE` | `文件 {fileName} 超过当前大小限制` |
| 任务不存在 | `INGESTION_JOB_NOT_FOUND` | `任务不存在或已过期` |
| 任务不可取消 | `INGESTION_JOB_NOT_CANCELLABLE` | `当前任务阶段不支持取消` |
| 任务不可重试 | `INGESTION_JOB_NOT_RETRYABLE` | `当前任务状态不支持重试` |
| 任务执行失败 | `INGESTION_JOB_FAILED` | `知识摄入任务处理失败，请查看任务详情` |

### 排序与去重

- 任务看板默认按 `updatedAt` 倒序展示，进行中的任务优先于终态任务。
- 单个文件的失败明细按输入文件原始顺序展示。
- 相同任务错误码、文件名和错误消息只展示一次。
- Chat 简单反馈只展示一条摘要，不重复输出后台阶段错误；详细错误在知识库任务详情查看。

## 验收标准

- [x] **AC-001**：用户通过文件上传提交一个合法文件后，系统先创建并持久化任务，再返回任务 ID；任务看板可以看到 `queued` 或后续执行状态。
- [x] **AC-002**：用户通过 Chat 调用 `wiki_ingest` 后，工具返回 `jobId`、`status=queued`、`executionMode=async` 和简单受理消息；Chat 不需要等待完整摄入完成。
- [x] **AC-003**：上传和 Chat 创建的任务在知识库任务看板使用相同的状态、进度、结果和错误字段。
- [x] **AC-004**：任务执行过程中，任务看板可以展示至少“排队中、解析中、AI 编译中、提交中、已完成、失败”对应状态或等价用户可读状态。
- [x] **AC-005**：应用重启后，已持久化但未完成的任务不会从任务列表消失；可恢复任务重新进入可执行状态，无法恢复的任务展示明确错误。
- [x] **AC-006**：多个任务同时提交时，系统不会因并发写入导致 Wiki 页面、索引、manifest 或图谱数据互相覆盖；最终提交顺序可在任务详情中追踪。
- [x] **AC-007**：批量任务中一个文件失败时，其他成功文件仍可完成并在任务结果中保留；任务状态为 `partial_failed`，失败文件有独立明细。
- [x] **AC-008**：任务看板对允许的任务提供重试、取消和详情操作；对不允许的状态显示标准错误文案且不执行非法操作。
- [x] **AC-009**：所有现有同步工具在未声明模式时保持同步行为；`wiki_ingest` 明确声明异步模式。
- [x] **AC-010**：第二阶段的 A2UI 任务卡片使用官方 v0.9 `createSurface`、`updateComponents`、`updateDataModel` 和 `deleteSurface` message，并以 `mint` Catalog 的 `IngestionTaskCard` 业务组件承载卡片内部 UI。
- [x] **AC-011**：第二阶段 A2UI 卡片的 `/job` 数据模型更新后，卡片能反映任务状态、进度、步骤和结果；A2UI 不绕过任务 API 直接修改任务状态。

## 反例

- 反例-001：Chat 调用 `wiki_ingest` 后，工具继续等待 AI 编译完成才返回。正确结果：异步工具完成任务持久化和入队后立即返回受理结果。
- 反例-002：只在内存 `Map` 中保存任务，应用重启后任务看板为空。正确结果：任务状态必须持久化到 SQLite，并具备恢复或明确失败口径。
- 反例-003：一个文件失败后删除同批次其他已成功生成的 Wiki 页面。正确结果：保留成功结果，任务进入 `partial_failed` 并展示失败明细。
- 反例-004：A2UI 消息使用自定义 `type=task_progress` 替代标准 `updateDataModel`。正确结果：任务卡片状态通过标准 A2UI Data Model 更新。
- 反例-005：A2UI 任务卡片把 `job` 作为协议顶层特殊字段。正确结果：`job` 放在 Surface Data Model 中，组件通过 `{ "path": "/job" }` 绑定。

## 非功能性需求

- **NF-001**：任务创建接口在输入校验通过且任务已持久化后返回，不等待完整摄入流程。
- **NF-002**：任务存储和队列接口不得暴露 SQLite 专属 API；未来可以替换为 Redis/BullMQ 适配器。
- **NF-003**：任务状态更新应具备幂等性；重复收到同一状态更新不得产生重复页面或重复任务结果。
- **NF-004**：任务看板支持断线后重新查询任务状态；不能只依赖一次性 SSE 事件才能恢复展示。
- **NF-005**：任务日志和错误信息不得默认把完整文件内容或 Base64 内容写入 Chat 消息和普通日志。
- **NF-006**：A2UI 只允许渲染客户端 Catalog 中登记的组件；未知组件不得执行任意代码。

## 风险与依赖

- 依赖项：现有 `WikiIngestionJobService`、`wiki_ingest`、Wiki 编译/图谱构建链路、SQLite 数据访问层、知识库前端模块和 Chat 工具事件系统。
- 风险项：现有 Chat 工具调用和上传任务的返回结构不同，统一任务结果时可能影响既有前端和测试。
- 风险项：Wiki 页面、索引、manifest 和图谱写入跨多个文件/存储步骤，单一事务无法覆盖全部操作。
- 风险项：A2UI 仍在演进，协议版本和 React Renderer 兼容性需要在设计阶段确认。
- 应对建议：先稳定领域任务模型和任务看板，再接入 A2UI；为任务存储、队列和 UI 适配分别保留接口边界。

## 待确认事项

- 任务看板是否需要保留超过 30 分钟的终态任务，以及终态任务的清理策略。
- 任务取消在进入 `committing` 后的精确语义：立即拒绝、等待当前文件完成，还是标记取消但保留已提交结果。
- 第一阶段是否需要对单个 Wiki 设置固定并发数，具体数值在设计文档中确定。
- 第二阶段实施时采用 A2UI `v0.9.1` 还是届时已稳定的更高版本；产品要求是使用标准 envelope 和 Catalog 机制。

## 规则来源说明

- 原始需求直接给出：知识摄入需要异步任务管理；范围仅覆盖知识摄入；不引入 Redis 但接口需要抽象；分两阶段交付；第一阶段 Chat 接入任务系统但只做简单工具反馈；第二阶段使用 A2UI 任务卡片；工具抽象同步/异步属性且 `wiki_ingest` 为异步。
- 产品补充口径：任务状态枚举、任务看板为事实来源、SQLite 持久化、任务错误 Contract、幂等性、A2UI Data Model 绑定和异常边界，用于将原始需求转化为可测试规格。
