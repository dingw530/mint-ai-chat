# LLM Judge Agent 评测

## 背景与目标

Mint 的 `agent-eval` 已能对答案关键词、引用身份、工具事件、审批和最终状态做确定性验证，但无法诊断开放式答案的事实正确性、证据支撑、完整性和可观察的决策轨迹质量。本变更在不弱化既有安全门禁的前提下，引入可校准的 LLM-as-a-Judge 评测层。

## 用户与场景

- 作为 Mint 维护者，我需要为每个评测用例声明可审计的语义 Rubric，以定位 Agent 在正确性、证据、完整性和轨迹方面的短板。
- 作为模型选型者，我需要在相同用例上运行 Judge，并在报告中区分确定性失败、语义评分和 Judge 不确定性。
- 作为评测维护者，我需要导出用于人工标注的校准样本，并可将人工金标与 Judge 结果对比。

## 范围

- 做：结构化 Judge Rubric（维度、等级、权重、陷阱和边界案例）的数据集校验。
- 做：将答案、引用、检索引用、可观察工具轨迹、最终状态和确定性结果提供给可注入 Judge。
- 做：OpenAI 兼容的 Judge CLI 配置、结构化 JSON 结果校验、报告聚合和静态 viewer 展示。
- 做：校准样本导出、人工标注对比和 Judge 一致性指标。
- 做：A/B 报告的交换位置配对评审与 Elo 相对排名。
- 做：新增 Wiki/RAG Judge Rubric 与单元测试。
- 不做：在 Mint 产品 UI 中展示评测入口、向生产流量自动采样、暴露模型隐藏思维链、替代审批/引用/最终状态等确定性验证。

## 业务规则

1. 确定性硬门禁优先：审批越界、确定性 Veto、引用身份和最终状态失败不能被 Judge 高分抵消。
2. Judge 只评价可审计输入；轨迹只包含工具名、阶段、状态、摘要和错误，不收集或要求隐藏思维链。
3. 每个 Judge Rubric 维度必须有 1–4 的可观察评分描述；`veto` 维度只能给出 pass/fail 规则。
4. Judge 必须返回结构化 JSON，包含逐维分数、关键失败、证据引用、置信度和简短理由；无效输出必须显式失败，不静默给分。
5. 不因回答长度加分；Rubric 可以声明最大建议长度，报告必须保留回答字符数以支持偏差审计。
6. 校准比较只接受同一 `caseId` 和 `runIndex` 的人工标注；Judge/Rubric 版本变化后需重新校准。

## 验收标准

- AC-1：数据集能声明并校验 Judge Rubric 的维度、评分档次、权重、陷阱和边界案例。
- AC-2：Runner 先执行确定性验证，再向注入 Judge 提供脱敏的答案、证据、轨迹、状态和确定性结果，并保存结构化 Judge 输出。
- AC-3：最终通过状态保持硬门禁语义；Judge 分数只在硬门禁通过后决定 `judgePassed`，Veto 或 Judge 关键失败会使 Judge 判定失败。
- AC-4：CLI 在显式 `--judge` 和 Judge 环境变量完整时调用 OpenAI 兼容 Judge；未显式开启时不产生 Judge 网络请求。
- AC-5：报告和 viewer 展示 Judge 通过率、加权分、维度分、关键失败、置信度、回答长度和确定性/Judge 的差异。
- AC-6：可导出待人工标注的校准 JSON，并能以人工金标生成一致率、平均绝对误差和待复核分歧。
- AC-7：Wiki/RAG 数据集至少包含一条带 Essential、Important、Optional、Veto、Pitfall 和边界案例的 Judge Rubric；单元测试覆盖正常评分、硬门禁短路、非法 Judge 输出和校准比较。
- AC-8：可对两份同数据集报告进行交换顺序的配对 Judge；位置不一致保守记为平局，并可计算 Elo 相对排名。

## 风险与依赖

- Judge API 依赖外部模型，默认不在测试中调用；使用注入 fake Judge 验证协议。
- LLM Judge 有长度、位置与同源模型偏差；本变更记录长度、支持多 Judge 结果，并通过校准导出/比较为人工审计提供基础，不在本次实现 Elo 排名。
- 实时模型质量只能通过隔离 Wiki、SQLite 和真实 API 运行验证；dry-run 仅验证框架。
