# Context Artifact 生命周期第一阶段产品规格

## 背景与目标

MINT 会将超过 12 KB 的工具结果保存到 `context-artifacts`，当前文件没有自动生命周期管理。长期运行会积累旧文件并占用本地磁盘。

第一阶段只解决两类清理触发：服务启动时清理过期 Artifact，以及写入新 Artifact 前接近容量上限时清理。第一阶段不增加定时清理机制。

## 用户故事

- US-001：服务重启后，用户不需要手动删除旧 Artifact，过期文件会被清理。
- US-002：工具结果写入前，系统会在接近容量上限时释放可回收文件，避免无界增长。
- US-003：清理失败或没有可回收文件时，当前工具调用应得到明确错误，不应静默丢失结果。

## 范围

### 做

- 基于 idle TTL 和 hard TTL 判断 Artifact 是否过期。
- 在 `startServer()` 监听 HTTP 服务前执行一次启动清理。
- 在大工具结果写入前检查预计容量，接近上限时执行清理。
- 保持现有 Artifact envelope、`read_artifact` 参数和 SHA-256 行为兼容。
- 增加单元测试覆盖过期、容量、路径隔离和清理失败场景。

### 不做

- 不增加定时器、后台 watcher 或定时清理任务。
- 不增加 Artifact 数据库表和公开管理 API。
- 不改变普通小工具结果的序列化行为。
- 不改变 Wiki 文件、A2UI UI Block 或用户消息的生命周期。

## 业务规则

- idle TTL：24 小时未修改的 Artifact；Context Artifact 当前是写入后不可变文件，因此不在读取时更新访问时间。
- hard TTL：创建后 7 天，无论访问频率如何都必须回收。
- 容量上限：1 GiB；预计写入后达到 80% 上限时触发写入前清理。
- 容量清理优先删除已过期文件；仍超过目标时按最早访问/修改时间删除超过 2 小时保护窗口的文件。
- 清理只能作用于配置的 Artifact 根目录及其会话子目录。
- 临时写入文件不得被清理器当作正式 Artifact 删除。
- 清理无法释放足够空间时，写入失败并返回可诊断错误。
- 同一进程内禁止定时清理；启动清理失败只记录日志，不阻止服务启动。

## 验收标准

- AC-001：启动清理删除 idle TTL 或 hard TTL 已到期的 JSON Artifact，保留未到期文件。
- AC-002：启动清理不删除 `.tmp` 文件、根目录外文件或受保护窗口内的文件。
- AC-003：新 Artifact 写入前，当预计容量达到 80% 上限时执行一次容量清理；低于阈值时不扫描删除。
- AC-004：容量清理按过期优先、时间最旧优先回收，并在释放不足时返回明确错误。
- AC-005：现有小结果、大结果 envelope、Artifact 路径和 SHA-256 行为保持兼容。
- AC-006：服务启动清理失败不会阻止 HTTP 服务启动，并产生结构化日志。
- AC-007：实现中不存在定时清理机制。
- AC-008：清理完成后删除 Artifact 根目录下变为空的会话目录，保留 Artifact 根目录和仍含有文件的目录。

## 风险与依赖

- 文件系统扫描和删除可能受到权限、并发写入或损坏文件影响，必须逐文件容错并记录失败。
- 本阶段仍是文件型存储，没有跨进程租约和用户管理界面；后续若需要强隔离，应引入 Artifact 元数据和会话授权。
