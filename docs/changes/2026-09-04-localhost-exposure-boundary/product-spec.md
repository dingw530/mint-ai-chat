# Product Spec: 本机 HTTP 与 Docker 暴露边界

## 背景与目标

Mint 是单用户、本地优先应用，当前没有 HTTP 用户认证、授权、会话隔离或远程访问审计。HTTP 服务未显式绑定 host，Docker Compose 又将 `3001:3001` 发布到所有宿主机接口，因而部署形态与单用户信任模型不一致。

本变更落实 TD-001 的方案 A：默认运行的 Node/Electron HTTP 服务只接受本机 loopback 连接；Docker 容器为容器网络监听，但官方 Compose 只把端口发布到宿主机 loopback。完成后，未认证的 Mint 不提供局域网或公网 HTTP 使用方式。

## 用户与场景

- 在本机通过浏览器、Electron 或 CLI 使用 Mint 的单用户。
- 在一台本机 Docker 主机上通过 `http://localhost:3001` 使用 Mint 的单用户。
- 审阅部署说明、需要确认 Mint 是否能安全暴露到局域网或公网的维护者。

## 用户故事

- US-001：作为本机用户，我希望默认服务只能从本机访问，以免同一网络中的其他设备直接调用我的 Mint API 和已保存的模型凭据。
- US-002：作为 Docker 用户，我希望官方 Compose 在容器内正常工作，同时宿主机端口不意外暴露给局域网或公网。
- US-003：作为维护者，我希望运行时、Compose 与安全文档表达同一边界，以免把 CORS 误认为认证或把无认证实例部署为远程服务。

## 功能范围

### FP-001：默认 Node/Electron 监听边界

1. 常规 Node 与 Electron 启动的 HTTP 服务必须显式绑定 IPv4 loopback `127.0.0.1`。
2. 端口冲突后的随机端口回退必须沿用同一绑定地址，不能因为回退而变成所有接口监听。
3. 监听模式必须是受限的内部启动契约；普通运行不得提供可把无认证服务绑定到任意网卡或 `0.0.0.0` 的公开配置。

### FP-002：Docker 容器与宿主机的双层边界

1. Docker 专用入口可让进程在容器网络内监听 `0.0.0.0:3001`，使 Docker 的端口转发能够抵达应用。
2. 官方 `docker-compose.yml` 必须将该容器端口只发布为 `127.0.0.1:3001:3001`；不得使用无 IP 前缀的 `3001:3001` 映射。
3. 官方 Docker 使用说明必须只给出 loopback 发布方式；不提供无认证局域网或公网发布示例。

### FP-003：安全契约与可验证性

1. 安全文档必须说明：CORS 不是访问控制；Mint HTTP 在本变更后仍无用户认证；远程访问不受支持。
2. 代码和配置验证必须覆盖常规监听、Docker 内监听、Docker Compose 宿主机映射和未知/不安全监听模式的拒绝或无法启用行为。
3. 发布前必须在实际 Docker 主机验证本机可连接、非 loopback 地址不能连接，并保存命令与结果作为 TD-001 证据。

## 非目标

- 不实现登录、API token、OAuth/OIDC、授权、会话管理、CSRF、防暴力破解、审计日志或多租户数据隔离。
- 不支持通过环境变量、Compose override、`docker run -p` 或反向代理将无认证 Mint 作为局域网/公网服务发布；用户自行绕过官方边界不属于受支持或安全的部署方式。
- 不修改 HTTP API、SSE 协议、CORS 允许列表、数据库 schema 或 Electron IPC 业务功能。
- 不保证仅靠应用监听设置抵御拥有宿主机/Docker 管理权的操作者；宿主网络规则与部署编排仍是外层责任。

## 业务规则

| ID     | 规则                                                                                                                 |
| ------ | -------------------------------------------------------------------------------------------------------------------- |
| BR-001 | 未认证 HTTP 服务在普通 Node/Electron 模式必须绑定 `127.0.0.1`，不能依赖 Node 的默认 host。                           |
| BR-002 | 若启动流程具备 Docker 内部模式，该模式只能由 Docker 专用入口启用，目标只能是 `0.0.0.0`；它不是远程访问开关。         |
| BR-003 | Docker 容器内部监听 `0.0.0.0` 时，官方 Compose 的宿主机发布必须仍为 `127.0.0.1:3001:3001`。                          |
| BR-004 | 不支持或未知的监听模式必须 fail closed（启动拒绝或回落为 loopback），不得默认为任意网卡监听。                        |
| BR-005 | CORS 仅是浏览器同源策略相关配置，不能作为认证、授权或网络暴露控制的证据。                                            |
| BR-006 | 任何未来的局域网/公网支持必须另立变更，先交付认证、授权、凭据/会话管理、审计、TLS/反向代理部署说明和未授权访问测试。 |

## 非功能要求

| ID     | 要求                                                                  |
| ------ | --------------------------------------------------------------------- |
| NF-001 | 既有本机浏览器、Electron、CLI 与 Docker health/use path 保持可用。    |
| NF-002 | 监听选择是确定、可单元测试的纯配置/启动策略，端口回退不改变安全边界。 |
| NF-003 | 运行日志不得把容器内 `0.0.0.0` 误表述为对宿主局域网或公网开放。       |

## 验收标准

- AC-001：以默认 Node 或 Electron 启动服务时，主监听与端口冲突回退监听均使用 `127.0.0.1`；不能从同机非 loopback IPv4 地址建立连接。
- AC-002：Docker 专用入口启动时，应用在容器内部监听 `0.0.0.0:3001`，并可由 Docker 的 loopback 端口映射转发访问。
- AC-003：官方 Compose 端口映射精确为 `127.0.0.1:3001:3001`；配置检查拒绝或报告无 IP 前缀、`0.0.0.0` 或其他外部宿主机发布形式。
- AC-004：不受支持、未知或试图让普通 Node/Electron 绑定任意网卡的监听配置不能让无认证服务对远程接口监听；相关单元测试覆盖该 fail-closed 行为。
- AC-005：`docs/SECURITY.md`、Docker 使用说明和 TD-001 记录明确“无认证 HTTP 仅限本机”、CORS 不是访问控制、远程服务不受支持，并链接后续认证路线的前置条件。
- AC-006：现有本机 HTTP API/CLI/Electron 启动相关回归测试通过；Docker 主机 smoke 证明 `localhost:3001` 可访问，选择一个实际非 loopback 宿主地址的同端口连接失败。若当前验证环境无 Docker 或无可用非 loopback 地址，必须记录为未验证，不能标记 TD-001 已完成。
- AC-007：完整 Harness 的 unit、coverage、boundary 通过；本变更无 UI 行为，browser-ac 按空场景记录为不适用。

## 风险与依赖

- Docker 容器内 `0.0.0.0` 是转发所需的内部监听，不等价于宿主机公开；实现和文档必须同时验证两层，不能只检查进程地址。
- `docker run -p 0.0.0.0:3001:3001`、host network、用户自建反向代理均可绕开官方 Compose 边界，故只能声明为不受支持而非应用层可强制防住的场景。
- IPv6 loopback、VPN/多网卡、Docker Desktop 网络实现可能影响实机 smoke 的取址；验收记录须注明实际 host、Docker runtime 和命令。
- 此变更降低默认暴露面，不替代未来远程产品路线所需的身份、授权和数据隔离设计。
