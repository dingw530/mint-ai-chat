# Wiki 检索基础优化

## 背景与目标

当前 Wiki 查询每次遍历 Markdown 文件并进行简单关键词匹配。随着页面接近方法论建议的规模，结果粒度粗、检索成本高，AI 还需要自行阅读整页才能找到证据。

本迭代落地一套不引入向量数据库的检索基础：段落级索引、SQLite FTS5 关键词召回、字段加权排序和可解释证据片段返回。

## 用户故事

- 作为 Wiki 用户，我希望搜索结果直接定位到相关章节和段落，而不是只返回整页。
- 作为 AI，我希望获得带匹配原因和生命周期信息的证据片段，以减少无关上下文。
- 作为系统维护者，我希望页面更新后索引可幂等重建，搜索不会依赖运行时遍历文件。

## 范围

### 做

- 从 Wiki 页面构建段落/章节级搜索文档。
- 使用 SQLite FTS5 索引标题、章节、正文、Claim 和路径。
- 对标题、章节、Claim、正文和路径实施可解释加权排序。
- 过滤 archived/superseded/deleted 页面，保留 active/stale 页面并应用生命周期权重。
- 返回匹配章节、证据片段和匹配类型。
- 保持 `paths` 精确读取模式兼容。

### 不做

- 本迭代不引入向量检索、Embedding 或 RRF。
- 本迭代不实现图谱遍历和查询意图分类。
- 本迭代不改变 Wiki 文件格式和已有页面内容。

## 业务规则

- 页面索引使用页面内容 hash，重复构建不得产生重复索引文档。
- 搜索结果必须只来自当前可读且未被 superseded、archived、deleted 的页面。
- 标题和章节命中权重大于正文命中；热度和生命周期只能作为相关性之后的轻量调整。
- 搜索结果最多返回请求的 `maxResults` 条；每条结果包含有限长度的证据片段。
- 无关键词或无结果时返回明确状态，不抛出内部错误。

## 验收标准

- AC-001：给定包含标题或章节关键词的查询，标题/章节命中的页面排序高于仅正文命中的页面。
- AC-002：给定查询，结果返回命中的章节、证据片段和至少一种匹配类型。
- AC-003：索引重建重复执行后，页面/Chunk 数量不重复增长，搜索结果稳定。
- AC-004：archived、superseded、deleted 页面不出现在默认搜索结果；stale 页面可以被召回但会被降权。
- AC-005：`paths` 模式仍可按路径读取页面，且不依赖 FTS 索引。
- AC-006：无关键词和无匹配查询返回可解释的空结果，不导致 API/工具失败。
- AC-007：既有 Wiki 搜索测试、生命周期测试和构建检查通过。

## 风险与依赖

- SQLite 构建必须通过 migration，不得直接修改数据库 schema。
- 现有 MCP 工具和 AI Wiki 工具需要共享同一检索实现，避免结果不一致。
- 中文分词能力有限时，先保留短语/英文标识符/路径精确匹配，后续再增加语义检索。
