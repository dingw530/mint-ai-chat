# AgentRun 统一事件契约产品规格

## 背景与目标

Mint 的 ReAct 运行已经通过 `ReactEventEmitter` 向 SSE、Electron IPC 和客户端发送 `runId`、序列号、工具、审批与终态事件，但运行编排仍直接依赖 `Sink`。工具审批被批准后会重新调用 `reactChat`，从而创建新的 run，导致一个用户任务的运行轨迹、前端状态和评测证据无法以同一 `runId` 连续关联。

本变更建立进程内 `AgentRun` 运行时契约：它统一管理一次聊天运行的状态、事件、终止和审批恢复；HTTP SSE、Electron IPC、客户端状态与评测均成为该契约的消费者。目标是在不改变既有聊天、工具审批和 A2UI 可见行为的前提下，使一次审批恢复保持同一运行身份，并让普通流式聊天与 ReAct 使用一致的事件外壳。

## 用户与场景

- 聊天用户在工具需要批准时，可以看到任务暂停；批准后同一条助手消息继续显示工具结果和回答，不出现第二条独立运行轨迹。
- Electron 与 Web 用户对相同的服务端运行接收同一语义和顺序的事件，切换会话不会把其他会话的状态写入当前界面。
- 开发者和评测维护者可以用统一事件序列复现一次运行的阶段、工具、审批、终态和基础 usage，而不依赖某一种传输实现。

## 用户故事

- US-001：作为聊天用户，我希望 ReAct 的状态、工具进度、回答增量和完成状态在 Web 与 Electron 中一致显示。
- US-002：作为需要批准敏感操作的用户，我希望批准或拒绝后仍能追溯为同一次任务，而不是看到新的运行身份。
- US-003：作为开发者，我希望增加 SSE、IPC 或评测消费者时不修改 Agent 编排核心。
- US-004：作为评测维护者，我希望取得完整且有序的运行事件和最终快照，用于断言工具策略、审批和最终回答。

## 范围

### 做

- 定义通用 `AgentRunEvent`、`AgentRunSnapshot`、终态与审批暂停语义，并保留当前 `runId`、`sequence` 和既有事件的兼容读取路径。
- 提取进程内 `AgentRun` 与运行注册表，使 ReAct、普通流式聊天、工具审批恢复都由统一运行时发出事件。
- 将 SSE、Electron IPC 和评测收集改为事件订阅/适配边界；运行核心不得直接依赖 `Sink`。
- 将批准/拒绝从“新建 `reactChat` 运行”改为“恢复或终止原 `AgentRun`”。
- 让客户端用同一事件校验与 reducer 路径消费 HTTP SSE 和 Electron IPC；继续以 `conversationId` 隔离显示状态。
- 为运行时、传输适配、审批连续性、事件序列和用户审批流程增加测试与 Harness 浏览器场景。

### 不做

- 不引入跨服务重启的运行恢复、持久化 Event Log、数据库迁移或新的公开 HTTP/Electron endpoint。
- 不改变 Agent 的工具权限策略、工具参数 schema、重试上限、上下文 Provider 位置、A2UI 协议或 Wiki 检索逻辑。
- 不将每个 token 或事件写入会话数据库；助手最终消息和既有 UI Block 持久化语义保持不变。
- 不在本变更中实现 Pi 的 TUI、JSONL session、CBOR 协议、Provider Catalog 或项目级信任模型。
- 不以本变更宣称实现真实 Provider cache usage、成本统计或跨进程 trace 采集；仅保留统一接入点和已知 usage 的透传。

## 业务规则

- 一个 `AgentRun` 绑定一个 `conversationId` 与不可变 `runId`；在其生命周期内事件序列从 1 严格递增。
- `run_completed`、`run_failed`、`run_cancelled` 是互斥终态；终态后不得发送新事件，也不得再次恢复。
- 审批请求使运行进入 `paused_for_approval`，不是终态。批准后执行原工具调用并在相同 `runId` 下继续后续模型轮次；拒绝后按既有错误/完成语义结束原 run。
- 运行快照是当前运行事实来源，事件只表示增量；快照和事件中的可变集合必须防御性复制，订阅者不得改变核心状态。
- 同一批并发工具可以按完成时间发送进度/结束事件，但写入下一轮模型上下文的 assistant/tool 消息仍须按模型返回的 tool-call 原始顺序排列。
- SSE 与 IPC 必须传递相同的序列化事件。客户端仅接受属于当前会话、当前 run 且序列号未回退的事件；旧 run、其他会话和终态后的事件不得污染前台状态。
- 普通流式聊天未使用工具时也必须发出 `run_started → answer_* → terminal` 的同类生命周期；既有纯文本渲染与打字机行为保持。
- 运行状态仅在进程内保存。服务或 Electron 主进程重启后，未完成 run 不恢复；客户端以已持久化消息和明确失败/空闲状态重新进入。

## 验收标准

- AC-001：一次 ReAct 运行产生带相同 `runId`、严格递增 `sequence` 的生命周期事件，且只产生一个终态；事件与快照的阶段、轮次和工具状态一致。
- AC-002：普通流式聊天和 ReAct 都通过统一事件契约向 SSE 和 IPC 传递状态；现有文本增量、思考、工具、A2UI、错误和取消展示不回归。
- AC-003：工具进入审批后，运行进入非终态暂停；批准时工具结束、后续回答和最终完成沿用原 `runId`，拒绝时不执行该工具且原 run 正确结束。
- AC-004：并发工具的结束事件可以乱序到达，但下一轮模型上下文中的工具结果保持 assistant 原始 tool-call 顺序；取消、工具错误和重复调用保护不回归。
- AC-005：HTTP SSE 与 Electron IPC 对同一事件对象使用同一解析/归约契约；跨会话事件、不同 `runId` 或序列号回退事件不会修改当前会话视图。
- AC-006：聊天用户可以在浏览器中发送触发工具的消息、看到等待审批、点击“批准执行”或“拒绝”，并看到对应的连续工具/回答终态与关键请求。
- AC-007：新增运行时、审批、客户端 reducer/传输和回归测试通过；服务端类型检查、客户端类型检查、边界检查及本变更完整 Harness 验证通过。
- AC-008：本变更不新增数据库 migration、端点定义、Provider 行为或逐事件持久化；变更路径符合计划中允许范围。

## 非功能要求

- NF-001：事件核心不依赖 Express Response、Electron `webContents` 或 React 类型，以便单元测试和评测直接消费。
- NF-002：单个订阅者抛错、断开或写入失败不得导致其他订阅者或 Agent 核心未受控崩溃；运行错误必须转换为既有终态事件。
- NF-003：运行时不改变现有会话切换语义：切换前台会话不取消后台 run；显式停止仍取消目标会话的运行。

## 风险与依赖

- `reactLoopCore`、`toolRoundEngine`、`toolApprovalService`、SSE 和 IPC 共用的事件边界影响面较大；必须先以兼容适配器迁移，不能一次替换所有消费者。
- 当前工作区有用户已有的 CI/验证脚本改动；本变更不得合并、覆盖或以其未提交状态作为交付证据。
- 浏览器场景依赖现有聊天 UI 的文本输入和审批按钮；实现阶段必须以真实 Vite 页面与 API mock 复验，而不是只断言 event JSON。
