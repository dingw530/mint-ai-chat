# 产品验证机制

## 概述

本 SKILL 解决 Vibe coding / 单人 AI 产品开发中的核心盲区——**没有外部反馈回路**。传统团队有产品经理、测试、用户反馈来告诉你"方向对不对"，单人项目全靠自觉。本 SKILL 提供一套**自体验证闭环**，用文档化的流程替代缺失的团队角色。

## 首次使用

调用本 SKILL 时会自动将三份模板文件从 `templates/` 复制到 `docs/product-manage/`（如已存在则跳过）。

## 适用场景

| 场景 | 建议 | 说明 |
|:----|:-----|:-----|
| 想到一个新功能想加 | ✅ 必须调用 | 走决策过滤流程 |
| 开始一个新分支/迭代 | ✅ 强烈建议 | 在写第一行代码前 |
| 感觉"该做某件事了"但说不清原因 | ✅ 必须调用 | 可能是焦虑驱动 |
| 用户使用中遇到卡顿 | ✅ 建议 | 确认是否已知问题 |
| 每周日 | ✅ 建议 | 执行每周回顾 |
| 日常对话式开发 | ⚠️ 选择性 | 如果对话聚焦于已确定的方向，不需要每次都调用 |

## 核心流程

```
  新想法 / 功能冲动
         │
         ▼
  ┌──────────────────────────────────────────┐
  │  ❶ 准入判断                               │
  │  "过去一周因缺失实际卡顿过吗？"            │
  │  ├── 是 → 进入 ❷                           │
  │  └── 否 → 写入「下周再说的功能清单.txt」   │
  │            封印 7 天                        │
  └──────────────────────────────────────────┘
         │
         ▼
  ┌──────────────────────────────────────────┐
  │  ❷ 自检确认                               │
  │  打开「开发前自检清单.md」过一遍           │
  │  确认：范围、验收标准、回滚方案            │
  └──────────────────────────────────────────┘
         │
         ▼
  ┌──────────────────────────────────────────┐
  │  ❸ 开发 & 自测                            │
  │  仅做清单中确认的内容                      │
  │  不做"顺便"功能                            │
  └──────────────────────────────────────────┘
         │
         ▼
  ┌──────────────────────────────────────────┐
  │  ❹ 每周复盘                               │
  │  周日打开「每周使用复盘模板.md」           │
  │  三问自答：满意/不爽/改一个               │
  └──────────────────────────────────────────┘
         │
         ▼
  ┌──────────────────────────────────────────┐
  │  ❺ 封印池清理                             │
  │  翻看「下周再说的功能清单.txt」             │
  │  ├── 7天后仍觉得需要 → 回 ❶ 重新准入     │
  │  └── 忘了/不想了 → 从清单中删除            │
  └──────────────────────────────────────────┘
```

## 三件套模板说明

本 SKILL 提供以下三份模板文档（位于 `templates/` 目录下），首次调用时会自动复制到 `docs/product-manage/`：

### ① 开发前自检清单.md（决策过滤器）
- **模板**：`templates/开发前自检清单.md`
- **作用**：刹车片，防止"感觉驱动"
- **调用时机**：每段开发开始前
- **核心问题**："过去一周因缺失实际卡顿过吗？"
- **不通过流向**：写入"下周再说的功能清单.txt"

### ② 每周使用复盘模板.md（仪表盘）
- **模板**：`templates/每周使用复盘模板.md`
- **作用**：积累真实使用数据
- **调用时机**：每周日 22:00
- **核心三问**：最满意？最不爽？只改一个？
- **重大价值**：发现趋势——连续三周"最不爽"指向同一问题，说明是真痛点

### ③ 下周再说的功能清单.txt（封印池）
- **模板**：`templates/下周再说的功能清单.txt`
- **作用**：杂物间，延迟判断
- **调用时机**：❌ 未通过准入判断时写入 | ✅ 每周复盘时翻看
- **关键规则**：封印期满但自己都忘了 → 直接删除，不算损失

## 行为指南

### 当用户说"我想加个功能"

1. 引导用户回答准入问题：**"过去一周，你因为少了这个功能而实际卡住过吗？"**
2. 如果是"觉得迟早要做"、"看起来挺酷"、"别人有我也要有" → 建议写入封印池
3. 如果是真实痛点 → 引导走「开发前自检清单」

### 当用户说"我想改个东西"

1. 先问"要解决什么具体的不爽？"
2. 如果回答模糊（"感觉不对"、"应该更好用"） → 建议先记录到周复盘，等数据积累
3. 如果回答具体（"查某某知识点时返回了错误答案"） → 走自检清单

### 当用户说"不知道接下来做什么"

1. 建议翻开「下周再说的功能清单.txt」看看封印中的条目
2. 如果有封印期满的 → 重新准入判断
3. 如果没有 → 劝退，去用户真实使用场景中积累不爽

### 当用户说"这个产品应该…"（开始画饼）

1. 温和但坚定地拉回：**"我们现在只验证一个事——自己用着顺不顺"**
2. 把饼记录到封印池，封印 7 天
