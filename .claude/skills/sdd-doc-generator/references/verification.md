# 验收与审计参考

在 L2 的 design、apply、verify 或用户明确要求审计时读取。L0 只需执行相关的最小验证。

## 验收证据矩阵

| 字段 | 要求 |
|---|---|
| 验收 ID | AC/DS/API/TP 标识 |
| 预期行为 | 可观察、可判定，不写“支持”“正常” |
| 实现位置 | 文件、模块、函数或组件 |
| 验证方式 | static / unit / integration / e2e / runtime / manual |
| 证据 | 测试名称、命令输出、日志、截图或复现步骤 |
| 状态 | 待验证 / PASS / FAIL / 未覆盖 |

规则：每条 AC 至少一行；跨模块、用户可见或外部进程行为至少需要 integration、e2e 或 runtime 证据；代码搜索、类型检查和文件存在只能作为 static 证据。存在 FAIL 或未验证项时不能标记阶段完成。

## Verify 检查项

完整审计至少检查：

1. 功能覆盖：spec 的 US/FP/AC 是否实现
2. 设计一致性：DS/API 与代码是否一致
3. Scope 偏差：代码是否多做或漏做
4. 记录完整性：exec-plan、traceability 与代码产出是否一致
5. 项目规范：目录、依赖方向、注释、测试和安全约定是否符合
6. 关键参数：超时、重试、截断、返回上限等是否与设计一致

若环境没有独立审计 agent，必须明确标记“审计能力降级”，不能把主 agent 自检冒充独立审计。

## 结论等级

| 等级 | 含义 |
|---|---|
| L0 | 仅有设计声明 |
| L1 | 有代码实现痕迹 |
| L2 | 局部单元测试通过 |
| L3 | 集成/端到端链路通过 |
| L4 | 独立一致性与规范审计通过 |
| L5 | 真实目标环境运行验证通过 |

报告同时写功能等级和审计状态；不能因为达到 L2 就宣称完整交付。
