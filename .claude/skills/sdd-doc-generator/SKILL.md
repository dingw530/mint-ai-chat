# sdd-doc

开发流程始于需求理解与澄清，随后生成三类核心文档：`product-spec`（产品规格/PRD）、`design-doc`（设计方案）、`exec-plan`（执行计划）。

## 命令参考

```
/sdd-doc-generator [spec|design|plan|apply|verify|check-doc|archive|pipeline|goal] [主题] [+补充约束]"
```

**参数规则**：第一个参数匹配文档类型（支持别名如 `prd`→`spec`、`方案`→`design`、`计划`→`plan`、`实现`→`apply`），后续合并为主题，`+`开头为补充约束。

| 命令 | 说明 |
|------|------|
| `discuss 主题` | 需求理解与澄清：复述需求理解、主动提出澄清问题、与用户对齐后进入下一步 |
| `spec 主题` | 理解需求并生成产品规格（用户故事、验收标准），需求模糊时主动澄清 |
| `design 主题` | 生成设计方案（多方案对比、接口定义） |
| `plan 主题` | 生成执行计划（任务拆解、验收方式） |
| `apply 主题` | 开发实现：据文档编码，逐 TP 推进 |
| `check-doc 主题` | 文档评审：检查完整性、追溯链路、质量 |
| `verify 主题` | 实现审计：隔离 agent 检查代码与文档一致性 |
| `archive 主题` | 归档已完成变更 |
| `goal 阶段 主题` | 自主执行模式：立即开始工作，自动推进到目标完成 |
| `pipeline 阶段1→阶段2 主题` | 串联多个阶段顺序执行，共享上下文；支持范围展开，`spec→verify` 自动补全中间阶段 |
| `changes` | 列出所有活跃变更 |
| _(无参数)_ | 交互式引导 |

**自然语言触发**：无参数时按关键词推断类型——讨论/理解/澄清/需求分析→discuss，需求/验收→spec，技术/方案→design，步骤/排期→plan，编码/实现→apply，检查/追溯→check，审计/审核→verify，自动/自主/循环→goal。

### check-doc — 文档评审

对变更进行文档完整性、追溯链路与质量评估，输出评审报告与评级，不修改文档。

**评审维度**：

| 维度 | 检查内容 | 等级 |
|------|---------|------|
| 结构完整性 | 文件齐全、模板完整、精简模式注明原因 | 必检 |
| 追溯链路 | ID 引用有效、无孤立项、traceability 同步 | 必检 |
| 信息质量 | 填充率、"待确认"残留、验收标准可验证 | 必检 |
| SPEC 可判定性 | 术语口径、枚举/字段映射、空值/边界、时间口径、错误 contract、反例是否明确 | 必检 |
| 方案决策 | design-doc 有 ≥2 方案、对比表、明确决策 | 选检 |
| 偏差记录完整性 | 已归档变更的 traceability 偏差记录中"后续动作"列非空的条目，是否有对应的设计文档更新 | 必检 |

**评级**（短板原则）：A=所有维度通过，B=主要通过少量改善，C=多维度不达标，D=关键缺失。

**流程**：扫描目录→解析 ID 验证追溯→统计填充率→检查偏差记录完整性→短板定级→输出报告。

**偏差记录完整性检查**：
扫描 traceability.md 偏差记录表，逐行检查"后续动作"列：
- 后续动作为"更新 design-doc" → 检查 design-doc 末尾是否有对应偏差补丁段
- 后续动作为"更新 product-spec" → 检查 product-spec 是否有对应更新
- 后续动作为"创建新变更" → 检查是否有对应的新变更目录
- 未找到对应更新的条目标记为"未处理"，计入评级

### verify — 实现审计

对代码实现进行全面审计。优先启动两个相互隔离的审计 agent，避免上下文惯性遗漏；如果当前运行环境没有 agent 调度能力，必须明确标记为“审计能力降级”，不得把主 agent 自检冒充独立审计。

| 检查项 | 严重级别 | 执行者 |
|--------|---------|--------|
| 功能覆盖：spec 中 US/FP/AC 是否实现 | ❌ 错误 | consistency-auditor |
| 设计一致性：DS/API 设计与代码一致 | ❌ 错误 | consistency-auditor |
| scope 偏差：代码与文档互有遗漏 | ⚠️ 警告 | consistency-auditor |
| 记录完整性：exec-plan vs 代码产出匹配 | ⚠️ 警告 | consistency-auditor |
| 代码规范合规：扫描项目约定文件，分析代码规范约束，检查代码是否合规 | ⚠️ 警告 | convention-auditor |
| 设计参数可追溯：design-doc 中声明的关键参数（截断值、超时等）在代码中有对应位置且值一致 | ❌ 错误 | consistency-auditor |
| 引导策略已实施：prompt 层面的规则已写入 system prompt，系统拦截已在权限检查中实现 | ⚠️ 警告 | consistency-auditor |
| 可靠性验证：标注为"中"/"低"的模块有实际运行数据证明可靠性，非仅凭设计断言 | ⚠️ 警告 | consistency-auditor |
| 边界规模测试：文件扫描/路径解析等逻辑的测试覆盖了 10+ 文件、嵌套目录、交叉链接的边界场景 | ⚠️ 警告 | convention-auditor |

**流程**：

1. **启动 consistency-auditor（文档一致性审计）**：隔离 agent → 读取变更文档 → 读取验收证据矩阵 → git diff 定位代码 → 正向追溯（文档→代码逐项检查）→ 反向追溯（代码→文档查遗漏）→ 输出审计报告。
2. **启动 convention-auditor（代码规范合规检查）**：隔离 agent → 扫描项目约定文件 → 分析代码规范约束 → git diff 定位代码 → 逐条检查合规性 → 输出审计报告。
3. **汇总报告**：合并两份审计报告和验收证据矩阵，按短板定级；任何未验证项都必须保留，不能用“代码存在”替代运行证据。

consistency-auditor 与 convention-auditor 彼此隔离，互不可见，确保各自判断不受对方影响。

### 验收证据矩阵

设计阶段必须为每个 AC、DS、API 和关键 TP 建立验收证据矩阵；矩阵是 apply 和 verify 的共同输入，不属于某个具体技术领域。

| 字段 | 说明 |
|---|---|
| 验收 ID | AC/DS/API/TP 标识 |
| 预期行为 | 可观察、可判定的行为，不写“支持”“正常”等模糊描述 |
| 实现位置 | 文件、模块、函数或组件 |
| 验证方式 | `static` / `unit` / `integration` / `e2e` / `runtime` / `manual` |
| 证据 | 测试名称、命令输出、运行日志、截图或可复现步骤 |
| 状态 | 待验证 / PASS / FAIL / 未覆盖 |

强制规则：

- 每个验收标准至少有一行矩阵记录；设计中声明的关键行为没有矩阵记录属于设计缺口。
- 代码搜索、类型检查和文件存在只能作为 `static` 证据，不能单独证明跨模块功能完成。
- 跨模块、用户可见或依赖外部进程的行为，至少需要 `integration`、`e2e` 或 `runtime` 证据。
- 每个 PASS 必须绑定具体证据；缺证据只能标记为“未验证”。
- 存在 FAIL 或未验证项时，阶段不能标记完成；若无法执行所需验证，应记录阻塞或“审计能力降级”。
- 代码中存在但文档没有的行为进入 scope 偏差记录；文档声明但代码没有的行为进入缺口记录。

### 审计结论等级

| 等级 | 含义 |
|---|---|
| L0 | 仅有设计声明 |
| L1 | 已有代码实现痕迹 |
| L2 | 局部单元测试通过 |
| L3 | 集成/端到端链路通过 |
| L4 | 独立一致性与规范审计通过 |
| L5 | 真实目标环境运行验证通过 |

verify 的结论必须同时报告功能等级和审计状态；不能因为达到 L2 就宣称完整交付。

### 审计后回写

verify 审计完成后，检查是否存在 scope 偏差（代码有但文档无的变更）：

1. 将审计报告中的"多做"项逐条录入 traceability.md 偏差记录
2. 对每条偏差评估影响等级：
   - **无影响**：纯内部重构 → 仅录入偏差记录
   - **行为修正**：补全边界处理 → 提示用户确认后在 design-doc 末尾追加偏差补丁段
   - **范围扩展**：新增能力 → 提示用户确认后更新 product-spec 或创建新变更
3. 用户确认执行更新后，在 design-doc/product-spec 末尾追加相应段落
4. 更新 exec-plan 执行记录中对应 TP 的备注

**使用示例**：
| 说法 | 效果 |
|------|------|
| `我们先讨论一下这个需求` | 需求理解与澄清，复述理解、提出疑问 |
| `写个 PRD：{主题}` | 生成 product-spec |
| `出个方案：{主题}` | 生成 design-doc |
| `拆解任务：{主题}` | 生成 exec-plan |
| `开始开发：{主题}` | 进入编码模式 |
| `帮我检查文档完整度` | 文档评审 |
| `审计代码是否按文档实现` | 实现审计 |

### pipeline — 流程串联

按顺序自动执行多个阶段，前一阶段的输出（如变更目录）自动传递给后续阶段。

**阶段顺序**（固定，用于范围展开）：
```
spec → design → plan → apply → verify → check-doc → archive
```

**语法**：
```
/sdd-doc-generator pipeline 阶段1→阶段2→阶段3 主题 [+补充约束]"
/sdd-doc-generator pipeline 阶段1→阶段N 主题 [+补充约束]"  # 范围展开
```

阶段间用 `→`（或 `->`）分隔。当前支持串联的阶段：`spec`、`design`、`plan`、`apply`、`verify`、`check-doc`、`archive`。

**范围展开**：当仅指定起止两个阶段时，自动按阶段顺序补全中间所有阶段。例如：
- `spec→verify` 展开为 `spec→design→plan→apply→verify`
- `plan→archive` 展开为 `plan→apply→verify→check-doc→archive`

**常用管道**：

| 管道 | 说明 |
|------|------|
| `spec→design→plan` | 完整文档生成 |
| `plan→apply→verify→archive` | 开发实施到归档 |
| `spec→design→plan→apply→verify→archive` | 全生命周期 |

**流程**：
1. **解析阶段序列**：按 `→` 拆分阶段名，校验每个阶段是否有效
2. **范围展开**：如果仅包含 2 个阶段且中间有其它阶段，按阶段顺序自动补全。如 `spec→verify` → `spec→design→plan→apply→verify`
3. 首个写入变更的阶段创建目录（`docs/changes/YYYY-MM-DD-{主题}/`），后续阶段共享该目录
4. 依次执行每个阶段，前一阶段失败则终止管道并提示
5. 所有阶段完成后更新 `traceability.md`
6. 输出各阶段执行摘要

**约束传递**：可在主题后附加全局约束（`+约束`），作用于所有阶段。

**使用示例**：

| 说法 | 效果 |
|------|------|
| `pipeline spec→design→plan {主题}` | 生成完整三件套文档 |
| `pipeline spec→verify {主题} +精简模式` | 范围展开：从 spec 到 verify 全流程 |
| `pipeline plan→archive {主题}` | 范围展开：从计划到归档 |
| `pipeline spec→design→plan→apply→verify→archive {主题} +精简模式` | 全生命周期（精简模式） |

## Goal 模式 — 自主执行

Goal 模式根据运行环境自动选用驱动机制：Claude Code 使用 `/goal` 双模型（主模型 + Haiku 评估器），Codex 使用 `create_goal` / `update_goal` / `get_goal` 工具。

### 命令

```
/sdd-doc-generator goal 阶段 主题 [+补充约束]
```

`阶段` 取值与 pipeline 一致：`spec`、`design`、`plan`、`apply`、`verify`、`check-doc`、`archive`，或全流程 `pipeline`。

### 流程

**Phase 1 — 需求澄清**（两平台一致，不可跳过）：以 spec 为首阶段时，必须先执行[生成流程 步骤0](#步骤0需求理解与澄清必选前置)中的全部要点——复述需求理解、提出澄清问题、用户确认对齐。禁止在未澄清的情况下直接进入 goal 模式。

**Phase 2 — 启动 Goal**（平台相关）：需求澄清完成后：

| 环境 | 启动命令 |
|------|---------|
| Claude Code | agent 输出 `/goal {stage} for {主题} according to /sdd-doc-generator rules. Stop when criteria met or ~{N} turns.`，用户回车 |
| Codex | agent 执行 `create_goal(objective: "{stage}: {主题}，完成条件: {完成标准}")` |

**Phase 3 — 自主循环**：启动后每轮自动决定下一步并按以下规则运行：

**结构化进度报告**（两平台一致）：每轮末尾输出以下区块供评估器/自检：

```
=== Progress ===
Stage: {当前阶段}
Done: {已完成事项}
Pending: {待完成事项}
Blockers: {阻塞项（若无则填"无"）}

=== Criteria Check ===
[PASS/FAIL] {条件1} — {证据，如命令输出}
[PASS/FAIL] {条件2} — {证据}

=== Next Action ===
{下一步操作 / 已完成}
```

**完成条件判定**：Claude Code 由 Haiku 评估器读 `=== Progress ===` 判定完成；Codex 由 agent 自检 `=== Criteria Check ===` 全部 PASS 后执行 `update_goal(complete)`。如果验收矩阵存在 FAIL、未验证项或审计能力降级，不得执行 `update_goal(complete)`。

**失败处理**：同一操作失败 2 次则换策略并记录原因；连续 3 次失败或检测到死循环（连续 3 轮相同尝试）时输出 `=== BLOCKER ===`（Claude Code 评估器标记失败，Codex 执行 `update_goal(blocked)`）。进度在每完成一个 TP 或阶段后立即写回文件。

### 各阶段完成标准

评估器（Claude Code）/ agent 自检（Codex）通过 `=== Criteria Check ===` 中的 PASS/FAIL 判定是否完成：

| 阶段 | 完成条件 |
|------|---------|
| spec | product-spec.md 创建，必填章节齐全，quality gate 自检 5 维度 PASS，关键字段无"待确认"残留 |
| design | design-doc.md 创建，≥2 方案对比 + 决策记录，所有 DS ID 关联到 spec ID，验收证据矩阵已建立 |
| plan | exec-plan.md 创建，追溯总览完整，所有 TP 初始化状态为"待启动"，验收证据矩阵已继承并初始化 |
| apply | 全部 TP 标记"已完成"，执行记录完整，验收证据矩阵已建立并逐项更新，self-check 通过 |
| verify | consistency + convention 双报告生成（或明确记录审计能力降级），矩阵无 FAIL/未验证项，合并定级，grade < B 时已修复 |
| pipeline | 以上依次通过，archive 完成，任一阶段连续失败 3 次则终止/标记 blocked |

## 追溯链约定（Traceability）

| 前缀 | 文档 | 含义 |
|------|------|------|
| US-/FP-/BR-/AC-/NF- | product-spec | 用户故事/功能点/业务规则/验收标准/非功能需求 |
| DS-/API- | design-doc | 设计决策/接口契约 |
| TP- | exec-plan | 执行任务 |

**追溯方向**：
```
product-spec            design-doc              exec-plan
US-001 ──────────────> DS-001 ──────────────> TP-001
FP-001 ────> DS-002 ──────────────> TP-002
AC-001 ──────────────────────────────> TP-003
```

design-doc 需在需求追溯表中注明覆盖情况（完全/部分/下一版），exec-plan 在追溯总览汇总全链路。文档更新时新增条目接续最大编号，不重排已有编号。

## 文档方法论

### Spec 编写六点框架（North Star）

有效 Spec 围绕 AI 输出的稳定性设计，不以长短为依据。以下六点构成 Spec 的基本骨架，各方法论章节和模板均围绕此框架展开：

| # | 要素 | 核心问题 |
|---|------|---------|
| 1 | **目标** | 用户/系统/流程在需求完成后获得什么能力？ |
| 2 | **范围** | 做什么 + 不做什么（明确非目标，防止过度发挥） |
| 3 | **约束** | AI 必须遵守的边界（安全、性能、兼容性） |
| 4 | **决策** | 不用 AI 重新设计的架构选择（使用哪个表、复用哪个组件、哪个状态枚举） |
| 5 | **任务** | 逐项推进的粒度——不在高上下文下一次性完成大功能 |
| 6 | **验收** | 正常流程、异常流程、边界场景、测试要求、灰度/监控 |

### product-spec — 定义"做什么" 
**适用场景**：需求澄清、范围定义、验收对齐
**核心问题**：这个产品要解决什么？为谁解决？怎么验证？
**必含章节**：背景与目标、用户与场景、用户故事、范围（含非目标）、业务规则、验收标准、风险与依赖
**要求**：语言清晰面向业务与协作方；验收标准可测试；未知写"待确认"禁止脑补。
**增强要求（涉及规则/状态/校验逻辑时强制启用）**：
- 术语与统一口径：定义状态、日期、时间、目标状态等关键术语，禁止用“正常”“合理”“支持多种情况”这类不可判定表述
- 数据模型与字段映射：当规则依赖字段/状态值时，写出字段路径、类型、枚举值、判定优先级
- 触发条件矩阵：写清楚“什么条件触发规则，什么条件不触发”
- 空值与异常口径：日期为空、数组缺项、字段冲突、老数据脏值时如何处理，必须显式说明
- 时间比较口径：明确时区、是否按自然日、是否忽略时分秒
- 父子/前后态比较基准：明确基于原状态还是本次操作后的目标状态
- 错误消息 contract：若存在拦截提示，定义展示字段、排序/去重规则、标准文案
- 反例：至少给出 2 个“容易误实现”的反例或边界例
  **禁忌**：
- 只写字段名不写枚举语义
- 只写“需要校验”不写空值/异常行为
- 只写“当前日期/当天”不写比较口径
- 在待确认前提下写死实现结论
  **精简模式**：可省略非功能性需求、风险与依赖章节；用户故事用 1-2 句简洁描述。

### design-doc — 定义"怎么做"

**决策来源区分**（参见六点框架第 4 点）：
执行过程中需根据用户输入判断决策来源：

| 场景 | 处理方式 |
|------|---------|
| 用户提供了具体决策（"用哪个表、复用哪个组件、接哪个接口"） | 直接按用户决策做设计，方案对比章节简写，在详细设计中体现决策约束 |
| 用户未提供决策，期望 agent 出方案 | 执行完整的 ≥2 方案对比 + 决策流程 |
| 用户表述模糊（"你出个方案吧"） | 先输出方案选项请用户选择，不要代用户决策 |

判断方法：如果在需求澄清阶段用户给出了"XX字段用之前的枚举""复用XX组件""接XX接口"等具体指引，视为场景1。

**适用场景**：技术方案设计、架构调整、关键决策评审
**核心问题**：有哪些可行方案？优劣？选哪个？为什么？
**必含章节**：背景与目标、约束与前提、方案选项（≥2）、方案对比、最终决策、详细设计、影响与风险、发布与验证、验收证据矩阵
**要求**：强调方案取舍；对现有系统改动须写清兼容性、发布与回滚。
**AI 工具设计补充要求**（当方案涉及 AI 工具/Agent 能力时强制启用）：
- **检测策略定义**：检查/判断类功能点必须写清检测方法、判断标准、误报/漏报边界。不止"检查X"，还要写"怎么检查"
- **共享能力分析**：对候选工具/模块做能力分析，标出需要相同基础能力的模块（文件读写、路径解析等），设计为共享模块而非各自实现
- **LLM 关键参数清单**：列出所有影响 LLM 行为的参数（截断值、超时、重试次数、返回条数上限），标注"更改需审"
- **LLM 引导策略**：包含引导策略——LLM 需理解的规则（prompt 层）、需系统强制执行的部分（权限拦截层）、需显式提供的信息（路径、结构）
- **可靠性等级标注**：每个功能模块标注可靠性等级：高（纯文件操作、无状态判断）、中（跨文件匹配）、低（涉及解析推测）。低可靠模块设计为可独立移除或委托
- **LLM 上下文一致性**：工具返回格式检查——同一份输出中不出现矛盾的格式暗示，数组结构优先于字符串拼接
**精简模式**：可省略方案选项/对比/最终决策章节，直接从约束跳到详细设计，在背景中说明方案唯一原因。

### exec-plan — 定义"如何落地"
**适用场景**：开发排期、任务拆解、执行协同
**核心问题**：分哪些阶段？每阶段做什么？谁能验收？怎么跟踪？
**必含章节**：目标与完成定义、背景与范围、前置条件、分阶段步骤、风险与依赖、验证与验收、验收证据矩阵
**要求**：步骤可执行可跟踪可验收；优先按阶段组织，避免松散 todo 列表。
**执行补充要求**：
- **文档一致性比对**：起草 exec-plan 时与 design-doc 逐项比对，确保对同一功能的描述不矛盾
- **矩阵初始化**：从 design-doc 继承验收证据矩阵，所有条目初始化为“待验证”，不得等到 verify 阶段才补写
- **细节反哺**：exec-plan 中新增的约束细节（如"文件名+内容匹配"）反哺到 design-doc 中更新
- **共享模块优先**：共享基础设施模块（如文件存在性检查）先于依赖它的工具实现
- **补丁计数器阈值**：为复杂模块标注补丁阈值（如 3 次）。达到阈值时触发架构重评估而非继续打补丁
- **可用性验证策略**：验证策略应与实现方案同样详细。写明测试范围、边界条件、规模覆盖
**精简模式**：可省略前置条件、风险与依赖；任务平铺代替分阶段结构。

## SDD 落地路径指引

当用户对 SDD 流程不熟悉或首次接触时，agent 应帮助用户渐进式采用，而非强推完整流程：

### 四步落地路径

1. **选高价值场景**：新模块开发、遗留系统迁移、外部平台接入。复杂度高、沟通成本高、返工成本高的场景引入 SDD 价值最明显
2. **定义轻量 Spec 模板**：从精简模式起步，只保留必要的章节
3. **建立项目级上下文**：沉淀项目原则、架构约束、目录规范、接口规范、权限模型等长期复用信息
4. **纳入研发流程**：需求进入开发前先写轻量 Spec → 关键边界评审 → AI 按 Spec 生成计划 → 开发更新 → 测试生成用例

### 采用节奏判断

| 用户状态 | 推荐做法 |
|---------|---------|
| 第一次用 SDD | 从精简模式 + spec→plan 管道起步。等用户感受价值后再引导完整流程 |
| 有过 SDD 经验但项目复杂 | 完整模式。强调约束、决策、验收章节 |
| 团队推行 SDD | 聚焦在"项目级上下文"沉淀——让团队先建立共享知识基底，再跑单次流程 |

### 什么时候不需要 SDD

以下场景直接用 Prompt 即可，无需启动 SDD 流程：

- 改文案、调样式
- 单一变量名重构
- 配置项变更
- 明确的一处 bug 修复（非连锁影响）

如果用户启动了 SDD 但评估后发现属于此范围，应主动提示"这个需求比较简单，直接实现可能更高效，是否需要跳过文档流程？"

如果介于中间（如新增一个小接口），启用精简模式。

## 精简模式

同时满足以下条件时启用：1-3 个功能点、路径单一、无跨团队依赖。裁剪规则：

| 文档 | 可省略章节 |
|------|-----------|
| product-spec | 非功能性需求、风险与依赖；用户故事简写 |
| design-doc | 方案选项/对比/最终决策，直接从约束跳到详细设计 |
| exec-plan | 前置条件、风险与依赖；任务平铺代替分阶段 |

精简模式下仍需分配追溯 ID，核心章节保留，并在背景中注明原因。信息量超预期时自动升级为完整模式。

## 非结构化输入到结构化 Spec

真实场景中需求往往以非结构化形式到达（客服反馈、会议纪要、聊天记录、邮件）。agent 需要在需求理解阶段将其转化为结构化 Spec。

### 通用转化流程

接收到原始输入后，按以下框架提取结构化要素：

| 原始输入中的信号 | 映射到 Spec 章节 |
|-----------------|----------------|
| "XX功能/页面报错/不可用" | 背景与目标 + 问题定级 |
| "影响范围是XX用户/XX订单" | 用户与场景 |
| "从XX入口进入，执行XX操作" | 复现路径 → 触发条件矩阵 + 验收标准 |
| "可能是因为XX原因" | 初步判断 → 数据模型 + 业务规则 |
| "XX模块不能动" | 范围（非目标） + 约束 |
| "修复后要满足XX条件" | 验收标准 |
| "涉及XX接口/权限/数据" | 约束 + 依赖 |
| "是否需要灰度/回滚" | 非功能性需求 + 风险 |

### 客服反馈转化示例

原始输入通常为："订单详情页打不开"。在流程中，agent 按以下框架将非结构化反馈整理为轻量 Spec：

1. **问题现象**：订单详情页打开失败（→ 背景与目标）
2. **影响对象**：某一类订单、某一批用户，还是所有用户（→ 用户与场景）
3. **复现路径**：从哪个入口进入，执行了什么操作（→ 触发条件矩阵 + 验收标准）
4. **相关上下文**：订单状态、用户身份、客户端版本、最近发布记录（→ 约束 + 数据模型）
5. **初步判断**：前端展示问题、接口异常、数据异常还是权限问题（→ 业务规则）
6. **修改范围**：涉及哪些模块、哪些模块不能动（→ 范围）
7. **验收标准**：什么情况下算修复完成（→ 验收标准）
8. **风险提示**：是否影响核心流程，是否需要灰度和回滚（→ 非功能性需求 + 风险）

**价值**：把非结构化反馈变成结构化任务。转化过程应在需求澄清阶段完成，与用户确认后再进入文档生成。

### 需求澄清 Prompts

需求理解的具体执行见[生成流程 步骤0](#步骤0需求理解与澄清必选前置)。在此基础上，当需求模糊时按六点框架顺序提问：

1. **目标**：最终希望达成什么效果？
2. **范围**：哪些场景覆盖？哪些不做？
3. **约束**：有什么强制限制？（安全、性能、兼容、合规）
4. **决策**：是否有已确定的方案方向（用什么表、复用哪个组件）？
5. **验收**：怎么判断完成？有参考案例吗？

**最低提问原则**：对于紧急/轻量需求，至少问清范围（做什么+不做什么）和验收标准。用户回复"你看着办"时在 spec 中标注"由 agent 补充设计"并推送到 design-doc 阶段处理。



## 生成流程

### 步骤0：需求理解与澄清（必选前置）

需求理解是整个流程的前置必选步骤，在开始文档撰写之前执行：

1. **阅读原始需求**：读取用户提供的所有材料
2. **复述理解**：向用户复述需求的背景/目标/核心问题/产出/验收方式
3. **主动澄清**：识别模糊、矛盾或缺失信息，提出澄清问题（"XX指什么？场景是否明确？有无参考案例？"）
4. **达成共识**：用户确认理解一致后进入下一步
5. **标记待确认**：未解答问题写"待确认"，禁止脑补
6. **识别不可判定表述**：模糊词（"合理、正常、自动处理"）、隐式状态/边界/依赖 → 在 spec 中补定义或标记待确认

`discuss` 命令：`/sdd-doc-generator discuss 主题` — 仅为需求理解与澄清，不生成文档。适合需求不明确、需要先对齐的场景。

`spec` 阶段自动包含上述步骤。pipeline 中以 `spec` 为首阶段时同样先执行需求理解。

### 步骤1：提炼输入
收集文档主题、业务背景/当前问题、目标用户或使用方、目标与非目标、已知约束、风险与待确认项。

### 步骤2：评估文档规模
| 判断维度 | 完整模式 | 精简模式 |
|---------|---------|---------|
| 功能点数量 | ≥ 4 个或不确定 | 1-3 个 |
| 改动路径 | 存在多个可行方案 | 路径单一、方案明确 |
| 协作范围 | 跨团队或多系统 | 单团队、单系统 |
| 文档受众 | 需多方评审对齐 | 主要用于内部记录 |

**草稿判断门**：评估后如果发现改动极小（改文案、调样式、单一变量重命名、配置变更），直接建议跳过 SDD 流程，用 Prompt 更高效。

### 步骤3：补齐上下文
- 将模糊目标改写为可执行表述，零散需求归并为功能点/步骤/决策项
- 用"待确认"标记未知信息
- **使用六点框架对齐**：按目标/范围/约束/决策/任务/验收的顺序检查当前 Spec seed 是否覆盖了所有要素。缺要素的在生成文档时标注"待补充"
- 如果用户输入是非结构化的（如聊天记录、邮件、反馈），按[非结构化输入到结构化 Spec](#非结构化输入到结构化-spec) 的流程进行转化
- **禁止**编造接口、字段、时间、负责人、未经确认的结论、无来源的实现细节
- 若需求包含状态流转、字段校验、父子关系、错误拦截、数据映射中的任一项，自动补一轮“可判定性检查”：
    - 是否缺字段路径/数据结构
    - 是否缺枚举值与状态判定口径
    - 是否缺空值/脏数据/冲突数据处理
    - 是否缺时间比较口径
    - 是否缺错误提示 contract
    - 是否缺反例或边界样例

### 步骤4：追溯编号
按顺序分配 ID（US-001, FP-001, DS-001, TP-001...）。检查 `docs/changes/` 下同主题目录或 `docs/product-specs/` 等目录下同名文件，继承最大编号。若生成 design-doc 或 exec-plan，自动关联对应 spec/design 建立追溯表。

### 步骤5：选择模板填充
模板位于 `templates/` 目录下。按步骤2判定的模式选择完整或精简模板，填充时自动关联上下级追溯 ID。

### 步骤6：生成 traceability.md
当具备 product-spec、design-doc、exec-plan 中至少两份文档时，基于 `templates/traceability.md` 模板自动生成追溯总览。模板包含全链路追溯表、偏差记录表（初始为空行）和快捷链接。偏差记录表必须保留，即使当前无偏差。

## 落库目录

```
docs/changes/YYYY-MM-DD-{主题}/
├── product-spec.md
├── design-doc.md
├── exec-plan.md
├── traceability.md
└── spec-increment.md
```

快捷索引目录（`docs/product-specs/`、`docs/design-docs/`、`docs/exec-plans/`）保留为 README 索引视图。

## 输出规范

- 中文、纯 Markdown、保留模板章节、信息不足写"待确认"
- 优先输出成品文档，不额外输出大段解释
- 若生成的是 `product-spec` 且命中了增强要求，默认保留以下章节：`校验触发时机`、`术语与统一口径`、`数据模型与字段映射`、`错误消息 Contract`、`反例`

## SPEC 质量闸门

在输出 `product-spec` 或执行 `check-doc` 时，按以下顺序自检；任一项不满足时，不要假装完整，应补写或标记待确认：

1. **可判定**：每条 BR/AC 是否能直接判断真伪，是否仍含模糊词
2. **可实现**：字段路径、枚举值、比较基准、异常行为是否足够让开发落地
3. **可测试**：是否能从 BR/AC 直接提取正例、反例、边界例
4. **可追溯**：新增的补充规则是否标明来源是“原始需求”还是“产品补充口径”
5. **可展示**：若失败需要提示，是否定义了错误文案和展示 contract

## 文档更新反馈

基于上一版更新时，正文后追加变更摘要与验证点：

```markdown
## 本次更新摘要
- 对比基线：{上一版标识}
- 新增/修改/删除：{以章节粒度归纳}
- 仍待确认：{...}

## 验证点
- 受影响验收标准：{...}
- 建议测试/回归点：{...}
- 发布观察点（可选）：{...}
```

## 执行与编码

用户发出"开始开发/实现需求/编码实现"等指令时进入编码模式。

### 执行流程

1. **准备**：定位当前变更的 exec-plan，traceability.md 状态改为**进行中**，初始化所有 TP 状态为"待启动"
2. **逐 TP 实现**：理解 TP 描述及关联 DS/AC → 按项目规范编码 → 对照 AC/DS 自验边界和异常 → 更新执行记录（状态改为已完成，记录产出文件、问题与偏差）
3. **同步**：每完成一个 TP 更新追溯总览和 exec-plan 执行记录；发现 scope 变更在 plan 追加新 TP；执行记录**只追加不覆盖**

### 偏差处理

发现代码偏离原设计时，在 traceability.md 偏差记录中追加条目（日期 / 类型(fix|refactor|feature|scope-change) / 涉及 TP / 涉及文件 / 变更原因 / 影响评估 / 后续动作），按影响执行：

| 影响 | 处理 |
|------|------|
| 无影响（内部重构） | 仅记录 |
| 行为修正（补边界） | 在 design-doc 末尾补偏差补丁段 |
| 范围扩展（改契约） | 更新 product-spec 或创建新变更 |

偏差补丁格式（追加到 design-doc 末尾）：

```
## 偏差补丁：{日期}

**触发偏差**：traceability.md 偏差记录第 {N} 条
**变更内容**：{DS-xxx 的哪个部分被修改}
**影响范围**：{受影响的模块/接口}
**与原设计的关系**：{修正 / 扩展 / 替代}
```

### 完成归档

1. 执行 `verify` 实现审计（隔离 agent 检查功能覆盖、设计一致性、scope 偏差、记录完整性）
2. 通过后：traceability.md 改为**已完成**并填写完成日期 → 更新快捷索引目录（`docs/product-specs/`、`design-docs/`、`exec-plans/`），design-doc 有版本追加段时在"最后修订"列反映最新版本 → 存档审计报告
3. 不通过则修复后重新审计

### Handoff
执行记录中写明当前进度、下一步、阻塞/风险、关键决策。接手 agent 第一件事读取执行记录。

## 核心原则

1. **未知信息写"待确认"，禁止脑补** — 检测策略未定义时标注"待确认"，禁止实现时自由发挥
2. `product-spec` 必须保留：用户故事、范围、验收标准
3. `design-doc` 必须保留：方案对比、最终决策、兼容与发布策略
4. `exec-plan` 必须保留：阶段目标、具体任务、验收方式
5. **执行阶段务必反向更新 exec-plan，保持文档与实际进度一致**
6. **输出结果应直接复制到 Markdown、飞书、Notion 等工具**
