# 产品验证机制

## 概述

本 SKILL 解决 Vibe coding / 单人 AI 产品开发中的核心盲区——**没有外部反馈回路**。传统团队有产品经理、测试、用户反馈来告诉你"方向对不对"，单人项目全靠自觉。本 SKILL 提供一套**自体验证闭环**，用文档化的流程替代缺失的团队角色。

---

## 调用流程

当此 SKILL 被触发时，按以下顺序执行：

### 步骤 0：初始化（仅首次）

检查 `docs/product-manage/` 下是否存在三份文件：

| 文件 | 检查路径 |
|------|---------|
| 开发前自检清单.md | `docs/product-manage/开发前自检清单.md` |
| 每周使用复盘模板.md | `docs/product-manage/每周使用复盘模板.md` |
| 下周再说的功能清单.txt | `docs/product-manage/下周再说的功能清单.txt` |

- 如果 **全部存在** → 跳过，直接进入步骤 1
- 如果 **部分或全部缺失** → 从 SKILL 的 `templates/` 目录复制缺失的文件到 `docs/product-manage/`，告知用户"已创建模板文件，请按需修改"

### 步骤 1：意图识别

根据用户输入判断场景，进入对应的处理分支：

| 用户意图 | 处理分支 |
|---------|---------|
| "加个XX功能" / "加个XX按钮" | → 分支 A：功能准入 |
| "改个东西" / "优化XX" | → 分支 B：改动确认 |
| "不知道做什么" | → 分支 C：方向探索 |
| "这个产品应该…" | → 分支 D：画饼拦截 |
| "做个复盘" / 周日 | → 分支 E：每周复盘 |

### 步骤 2：执行分支引导

进入对应分支处理（见下文"行为指南"）。

## 适用场景

| 场景 | 建议 | 说明 |
|:----|:-----|:-----|
| 想到一个新功能想加 | ✅ 必须调用 | 走决策过滤流程 |
| 开始一个新分支/迭代 | ✅ 强烈建议 | 在写第一行代码前 |
| 感觉"该做某件事了"但说不清原因 | ✅ 必须调用 | 可能是焦虑驱动 |
| 用户使用中遇到卡顿 | ✅ 建议 | 确认是否已知问题 |
| 每周日 | ✅ 建议 | 执行每周回顾 |
| 日常对话式开发 | ⚠️ 选择性 | 如果对话聚焦于已确定的方向，不需要每次都调用 |

## 三件套模板说明

本 SKILL 提供以下三份模板文档（位于 `templates/` 目录下），首次调用时会自动复制到 `docs/product-manage/`：

### ① 开发前自检清单.md（决策过滤器）
- **模板**：`templates/开发前自检清单.md`
- **作用**：刹车片，防止"感觉驱动"
- **调用时机**：每段开发开始前
- **核心问题**："过去一周因缺失实际卡顿过吗？"
- **不通过流向**：写入"下周再说的功能清单.txt"

### ② 每周使用复盘模板.md（仪表盘）
- **模板**：`templates/每周使用复盘模板.md`
- **作用**：积累真实使用数据
- **调用时机**：每周日 22:00
- **核心三问**：最满意？最不爽？只改一个？
- **重大价值**：发现趋势——连续三周"最不爽"指向同一问题，说明是真痛点

### ③ 下周再说的功能清单.txt（封印池）
- **模板**：`templates/下周再说的功能清单.txt`
- **作用**：杂物间，延迟判断
- **调用时机**：❌ 未通过准入判断时写入 | ✅ 每周复盘时翻看
- **关键规则**：封印期满但自己都忘了 → 直接删除，不算损失

## 行为指南（AI 执行步骤）

### 分支 A：功能准入

当用户说"我想加个功能"时：

1. **问准入问题**：*"过去一周，你因为少了这个功能而实际卡住过吗？"*
2. **判断结果**：
   - 如果是真实痛点（实际卡住过）→ 打开 `docs/product-manage/开发前自检清单.md`，逐项引导用户过一遍
   - 如果是"觉得迟早要做"、"看起来挺酷"、"别人有我也要有" → 打开 `docs/product-manage/下周再说的功能清单.txt`，追加一行（格式：`YYYY-MM-DD | 功能描述 | 来源 | 待定`），告知用户"已封印 7 天，X 天后记得回来看看是否仍然需要"

### 分支 B：改动确认

当用户说"我想改个东西"时：

1. **追问具体问题**：*"要解决什么具体的不爽？"*
2. **判断清晰度**：
   - 回答模糊（"感觉不对"、"应该更好用"）→ 建议先记录到每周复盘，等数据积累。打开 `docs/product-manage/每周使用复盘模板.md`，在历史记录区域追加一条待办
   - 回答具体（"查 XX 时返回了错误答案"）→ 打开 `docs/product-manage/开发前自检清单.md`，逐项引导

### 分支 C：方向探索

当用户说"不知道接下来做什么"时：

1. **检查封印池**：打开 `docs/product-manage/下周再说的功能清单.txt`，查看是否有封印中的条目
2. **判断结果**：
   - 有封印期满（≥7天前写入）的条目 → 逐条问用户"这个还需要吗？"
     - 需要 → 回分支 A 重新准入
     - 不需要 → 从清单中删除
   - 没有条目或所有条目已处理 → 告知用户"暂时没有积压需求，建议回到真实使用场景中积累不爽，不要凭空想功能"

### 分支 D：画饼拦截

当用户说"这个产品应该…"（开始画饼）时：

1. **温和拉回**：*"我们现在只验证一个事——自己用着顺不顺"*
2. **记入封印池**：打开 `docs/product-manage/下周再说的功能清单.txt`，追加一条记录，封印 7 天
3. **说明规则**：*"已记录到封印池，7 天后如果你还在意这个，我们再认真讨论"*

### 分支 E：每周复盘

当用户说"做个复盘"或检测到是周日时：

1. **打开复盘模板**：读取 `docs/product-manage/每周使用复盘模板.md`
2. **逐问引导**：让用户依次回答三个问题（最满意 / 最不爽 / 改一个），将回答填入模板
3. **顺便清理封印池**：打开 `docs/product-manage/下周再说的功能清单.txt`，检查是否有封印满 7 天的条目：
   - 问用户"之前封印的 XX 功能，现在还觉得需要吗？"
   - 如果不需要 → 删除
   - 如果需要 → 引导走分支 A
4. **趋势检查**：翻阅历史记录，如果同一个问题连续 3 周出现在"最不爽"中，标记为**真痛点**，建议立即进入开发前自检清单
